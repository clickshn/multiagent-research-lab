## 1. 계정 ID · IAM 사용자명 노출 — **인지하고 내린 판단 (고칠 일 아님)**

> **결론: 커밋 히스토리를 재작성하지 않는다. 앞으로 새로 쓰는 문서에서 마스킹하는 것만 지킨다.**

### 사실관계 (이번 세션에 전수 확인)

| 대상 | 검사 범위 | 결과 |
| --- | --- | --- |
| **AWS 계정 ID (12자리)** | 커밋 이력 전체(`git log --all -p`) + 추적 중인 모든 `.md`/`.tf`/`.json`/`.sh`/`.py` | **0건 — 어디에도 없다** |
| ARN 형태 계정 ID | 커밋 이력 전체 | **0건** |
| **IAM 사용자명** | 추적 파일 | **`docs/handoff/session-07.md` 3곳** |
| `terraform.tfstate` / `terraform.tfvars` | 추적 여부 | **둘 다 `.gitignore` 대상 — 커밋 안 됨** |

**즉 실제로 푸시된 것은 IAM 사용자명 하나이고, 계정 ID는 애초에 나간 적이 없다.**
(레포는 이미 **공개** 상태라 이 노출은 이미 발생한 것이다 — 되돌릴 수 없다.)

### 판단 근거

1. **액세스 키 없이 계정 ID와 사용자명만으로 할 수 있는 것이 없다.** 이 사용자는
   **콘솔 로그인이 비활성**이다.
2. **실질적 방어는 §3의 IAM 권한 축소 쪽이다.** 권한이 좁아지면 **이름이 알려져도
   정찰 가치가 사라진다.** ADR-017의 Consequences에 이 의존 관계를 명시했다 —
   **ADR-017이 적용돼야 이 판단이 성립한다.**
3. **비용 대비 이득이 안 맞는다.** 히스토리 재작성은 v1.0 태그와 푸시된 커밋 23개를
   전부 갈아엎는 작업인데, 그렇게 해서 막는 것이 없다.

### 그래서 앞으로 지키는 것 (하나뿐)

- **새로 쓰는 문서에서 계정 ID·IAM 사용자명을 마스킹한다.** 이번 세션 산출물은 전부 그렇게 썼다:
  - `infra/iam/deploy-*.json` — 계정 ID 자리를 `ACCOUNT_ID` 자리표시자로 두고 커밋.
    렌더링 결과(`infra/iam/.rendered/`)는 `.gitignore` 대상이다.
  - `infra/iam/apply_least_privilege.sh` — **사용자명을 코드에 적지 않는다.**
    호출자 ARN에서 뽑는다 (`IAM_USER` 환경변수로 덮어쓰기 가능).
  - ADR-017 본문 — 사용자명을 쓰지 않고 "배포자 IAM 사용자"로만 지칭한다.

> ⚠️ **이미 나간 `session-07.md`의 사용자명은 그대로 둔다.** 지우면 "왜 이 판단을 했는지"의
> 맥락이 사라지고, 지워도 히스토리에는 남는다. **이 문단이 그 결정의 기록이다.**

## 2. EFS 쓰기 검증 — 세션 7의 미확정 항목

세션 7의 헬스체크는 **마운트만** 증명했다(마운트 실패 시 태스크가 뜨지 않으므로).
**non-root uid 10001이 실제로 쓸 수 있는지는 별개**였다 — 액세스 포인트의 `creation_info`
소유권 설정이 의도대로 먹었는지가 초점이다.

**증명하려면 두 번 돌려야 한다.** `build_index.py`는 **트레이스를 남기지 않는다**
(코드 확인: `scripts/build_index.py`에 tracer 호출 없음). 따라서

| 실행 | 증명되는 것 |
| --- | --- |
| `bash infra/run_task.sh index` | `/chroma` 액세스 포인트에 uid 10001이 쓸 수 있다 |
| `bash infra/run_task.sh research "질의"` | **`/traces`에 트레이스 JSONL이 실제로 기록된다** (+ 인덱스를 EFS에서 읽는다) |

### 결과 — **확정. uid 10001이 EFS 세 디렉터리를 모두 쓴다.**

| 실행 | 태스크 | 결과 |
| --- | --- | --- |
| `index` | `f3786de3…` | **exitCode=0.** `/app/var/chroma`에 16건 인덱싱 9.6s, 컬렉션 문서 수 16 |
| `research "멀티에이전트 검증 루프의 한계는?"` | `a366bc8b…` | **exitCode=0.** **인덱스 문서 수 16** (← 이전 태스크가 쓴 것을 읽었다), `var/traces/20260916-060222-48174b.jsonl` 기록 |

**세 가지가 한꺼번에 증명됐다.**

1. **쓰기** — `index` 태스크가 `/chroma` 액세스 포인트에 썼다. 액세스 포인트의
   `creation_info`(uid/gid 10001)가 의도대로 먹었다.
2. **영속성** — `research` 태스크는 **별개의 태스크**인데 "인덱스 문서 수 16"을 읽었다.
   Fargate 로컬 스토리지는 태스크와 함께 사라지므로, 이 값이 나왔다는 것은
   **인덱스가 EFS에 남아 태스크 경계를 넘었다**는 뜻이다. ADR-015가 노린 것이 이것이다.
3. **트레이스 쓰기** — ⚠️ **로그 한 줄로 판단하지 않았다.** `src/obs/tracer.py`를 확인했다:
   `_JsonlTrace._write`(L191‑193)와 `LocalJsonlTracer.__init__`의 `mkdir`(L220)에는
   **try/except가 없다** — 예외를 삼키는 `except`는 전부 L263 이후 Langfuse 클래스에만 있다.
   따라서 `/traces`에 쓸 수 없었다면 `PermissionError`가 그대로 올라와 **태스크가 0이
   아닌 코드로 죽었을 것이다.** `exitCode=0`으로 끝났다는 사실이 쓰기 성공의 증거다.

**시크릿 마스킹도 CloudWatch Logs에서 다시 확인됐다:**
`host='***.ktcloud.com'`, `endpoint_fp='1897f0ecc081'` — **세션 7과 같은 지문**이므로
같은 엔드포인트다(캐시를 비울 이유가 없다, ADR-008).

### 곁가지로 나온 것 두 가지

**(가) 콜드 스타트 표본이 n=1 → n=3이 됐다.** 세션 7의 "이미지 크기가 지배 요인이 아니다"가
보강됐다.

| 실행 | 프로비저닝 | **이미지 풀** | 기동 | 콜드 스타트 합계 |
| --- | ---: | ---: | ---: | ---: |
| session-07 healthcheck | 19.19s | 22.22s | 19.38s | 60.79s |
| session-08 index | 21.42s | 21.52s | 11.89s | 54.83s |
| session-08 research | 13.21s | 22.04s | 11.75s | 46.99s |
| **평균** | 17.94s | **21.93s** | 14.34s | **54.20s** |

**이미지 풀이 가장 안정적이다** (21.52~22.22s, 폭 0.7s). 흔들리는 것은 프로비저닝
(13.21~21.42s)과 기동(11.75~19.38s)이다. **평균으로도 풀(21.93s) < 프로비저닝+기동(32.28s)**
이므로 세션 7의 결론이 유지된다 — **이미지 축소의 기대 이득은 작다.**

**(나) 이 질의는 4개 항목 전부 "근거 없음"으로 끝났다.** 코퍼스에 에이전트 논문이 있는데도
그렇다. **README §5.2의 검색 재현율 문제가 클라우드에서도 그대로 재현된 사례**이고,
동시에 **지어내지 않는다는 요구가 지켜진 사례**이기도 하다 — 모델이 알고 있을 법한
주제인데 한 문장도 만들지 않았다. Verifier 호출이 0회인 것도 설계대로다(인용 0개인 항목은
모델을 부르지 않고 기계 판정으로 거른다, ADR-006).

## 3. 배포자 IAM 최소 권한 (ADR-017)

세션 7이 "다음 세션 항목"으로 남긴 것이다. **아이러니가 그대로 기록돼 있었다** —
같은 세션이 태스크 역할에는 `ClientRootAccess`를 주지 않고 액세스 포인트 경유만 허용하면서,
그것을 배포한 사용자에게는 서비스 단위 관리형 정책을 통째로 붙였다.

### 산출물

| 파일 | 내용 |
| --- | --- |
| `infra/iam/deploy-core.json` | 네트워크(EC2/VPC) · EFS · Budgets — `aws:RequestedRegion`으로 서울에 가둠 |
| `infra/iam/deploy-app.json` | ECR · ECS · Logs · SSM · IAM 역할 — 대부분 프로젝트 접두사 ARN으로 가둠 |
| `infra/iam/apply_least_privilege.sh` | `show` / `free-slots` / `attach` / `detach` / `rollback` |

### 설계에서 걸린 것 세 가지

1. **인라인 정책으로는 불가능하다.** IAM 사용자 인라인 정책은 **2,048자** 제한인데,
   필요한 액션 목록은 공백 제거 기준 **core 2,287자 / app 3,600자**다. 고객 관리형 정책
   (6,144자)으로 간 것은 취향이 아니라 제약이다.
2. **`iam:AttachRolePolicy`를 그냥 열면 권한 상승 경로가 된다.** 프로젝트 역할에
   `AdministratorAccess`를 붙인 뒤 태스크로 실행하면 된다. `iam:PolicyARN` 조건으로
   **Terraform이 실제로 붙이는 `AmazonECSTaskExecutionRolePolicy` 하나만** 허용해 닫았다.
   `iam:PassRole`도 역할 2개 + `ecs-tasks.amazonaws.com`로 제한했다.
3. **`iam:AttachUserPolicy`는 일부러 넣지 않았다.** 넣으면 "최소 권한"이 스스로를
   관리자로 승격할 수 있다는 뜻이 된다. ⚠️ **그 대가로 롤백 경로가 루트 계정 콘솔뿐이다** —
   `detach` 전에 루트 로그인 수단이 살아 있는지 확인해야 한다.

### 순서를 스크립트가 강제한다 — **붙이고 → 확인하고 → 뗀다**

```
show → free-slots → attach → ./apply.sh plan → detach → ./apply.sh plan   ← 마지막이 진짜 검증
```

반대로 하면 중간에 권한이 하나도 없는 구간이 생기고, 거기서 실패하면 되돌릴 권한조차 없다.
`detach`는 분리한 정책 ARN 목록을 `infra/iam/.rendered/detached-*.txt`에 남긴다(롤백 근거).

### 교체 전 상태 — **관리형 정책 10개** (세션 7 기록보다 5개 많다)

```
AmazonEC2ContainerRegistryFullAccess      AmazonSSMFullAccess
AmazonEC2ContainerRegistryPowerUser       AmazonElasticFileSystemFullAccess
IAMFullAccess                             CloudWatchLogsFullAccess
AmazonECS_FullAccess                      AmazonVPCFullAccess
CloudWatchLogsReadOnlyAccess              AWSBudgetsActionsWithAWSResourceControlAccess
```

인라인 정책은 없다. **세션 7 핸드오프는 5개로 기록했는데 실제로는 10개다** — 그 뒤에
EFS·IAM·Budgets·Logs Full이 추가로 붙었고 기록되지 않았다. (핸드오프에 남기지 않으면
이렇게 벌어진다는 사례로 남긴다.)

**두 가지가 두드러진다.**

1. ⚠️ **`IAMFullAccess`가 제일 크다.** 이 사용자는 역할을 새로 만들어 아무 정책이나 붙일 수
   있으므로, **ADR-015가 태스크 역할에 건 격리(액세스 포인트 경유만, `ClientRootAccess`
   미부여)를 그냥 우회할 수 있다.** `docs/governance.md`가 "IAM 통제 위에 계정 관리자가
   있다"고 적어 둔 그 주체가 **다름 아닌 배포자 본인**이라는 뜻이다. ADR-017이 닫으려는
   것이 정확히 이 구멍이다.
2. **중복 2쌍** — ECR Full ⊃ PowerUser, CloudWatchLogs Full ⊃ ReadOnly.
   10개지만 실질 영역은 8개다. **권한이 실패할 때마다 하나씩 붙은 흔적**이다.

`AWSBudgetsActionsWithAWSResourceControlAccess`도 이름보다 넓다 — Budgets Action이
IAM 정책을 적용하거나 리소스를 정지시킬 수 있는 권한을 포함한다. 예산 **알람 1개**를
만들려고 붙기에는 과하다 (`budget.tf`는 `aws_budgets_budget` 하나뿐이다).

### 적용 절차 (사람이 실행 — `aws`는 `deny` 대상)

```bash
bash infra/iam/apply_least_privilege.sh show
bash infra/iam/apply_least_privilege.sh free-slots   # 한도 10개 — 중복부터 뗀다
bash infra/iam/apply_least_privilege.sh attach
cd infra/terraform && ./apply.sh plan     # 기존 정책이 아직 붙어 있는 상태에서 확인
CONFIRM=yes bash infra/iam/apply_least_privilege.sh detach
cd infra/terraform && ./apply.sh plan     # ← 최소 권한만으로 도는지, 이것이 진짜 검증
```

`plan`이 "No changes"로 끝나면 성공이다. 실패하면 메시지에 부족한 액션이 찍히므로
`infra/iam/deploy-*.json`에 추가하고 다시 `attach`한다 — **`detach` 전에 하는 것이 낫다.**

⚠️ **`detach` 뒤에는 정책을 고칠 수도, 다시 붙일 수도 없다.** `iam:AttachUserPolicy`뿐
아니라 `iam:CreatePolicyVersion`도 넣지 않았기 때문이다 — 넣으면 자기 정책에
`AdministratorAccess` 상당을 써 넣을 수 있어 최소 권한이 무의미해진다.
**이것이 자기제한(self-limiting)의 본질적 대가이고, 롤백·수정 경로는 루트 콘솔뿐이다.**
`detach` 전에 루트 로그인 수단이 살아 있는지 확인할 것.

### 알려진 IAM 특이사항 하나를 미리 반영했다

`logs:DescribeLogGroups`는 **리소스 수준 권한을 접두사 패턴으로 좁히면 거부되는 경우가
있다.** 로그 그룹 메타데이터 조회라 위험이 낮으므로 `log-group:*`(해당 계정·리전)로
별도 statement를 뒀다. 나머지 `logs:*`는 `/ecs/multiagent-research-lab/*`에 묶여 있다.

**정책 크기:** core 2,287자 / app 3,600자 (공백 제거, 관리형 한도 6,144자).

### 실행 결과 — **적용됨. `plan`이 최소 권한만으로 통과했다.**

| 단계 | 결과 |
| --- | --- |
| `attach` (1차) | ❌ **`LimitExceeded: PoliciesPerUser: 10`** — 이미 10개가 붙어 있었다 |
| `free-slots` | 중복 2개 분리 (ECR PowerUser, Logs ReadOnly) — **유효 권한 손실 0** |
| `attach` (2차) | ✅ 정책 2개 부착 |
| `./apply.sh plan` (기존 정책 병존) | ✅ **No changes** |
| `detach` | ⚠️ 8개 중 **7개 성공, 1개 실패** (아래) |
| **`./apply.sh plan` (최소 권한)** | ✅ **No changes — 이것이 진짜 검증이다** |
| `detach` (재시도) | ❌ **`AccessDenied: iam:DetachUserPolicy`** |

**최종 상태: `deploy-core` + `deploy-app` + `AWSBudgetsActionsWithAWSResourceControlAccess` 1개.**

### 여기서 드러난 것 네 가지 — **전부 설계에서 놓친 것이다**

**(1) `PoliciesPerUser`는 10개다.** 이미 10개가 붙어 있으면 **"붙이고 나서 뗀다"는 순서가
성립하지 않는다.** ADR-017이 안전 속성으로 내세운 순서 자체가 실행 불가였다.
해법은 **유효 권한을 하나도 잃지 않는 중복 정책부터 떼는 것**이었다 —
ECR PowerUser ⊂ ECR FullAccess, Logs ReadOnly ⊂ Logs FullAccess. 둘 다 함께 붙어 있던
FullAccess의 부분집합이라 떼어도 할 수 있는 일이 줄지 않는다. `free-slots`로 스크립트에
넣었다. **중복이 없었다면 이 방법도 없었다** — 그때는 순서를 깨거나 루트를 써야 한다.

**(2) `--output text`의 `\r`가 마지막 원소 하나만 망가뜨렸다.** 8개 중 7개가 성공하고
마지막 하나가 `ARN ... is not valid`로 실패했다. Windows CLI 출력이 `\r\n`으로 끝나는데
`tr '\t' '\n'`만 하면 **마지막 원소에만 `\r`가 붙는다.** `tr -d '\r'`를 추가해 고쳤다.
⚠️ **이 증상은 권한 문제로 오인하기 쉽다** — 실제로 그렇게 오인했다. 7/8이라는 패턴이
원인을 가리켰다.

**(3) 분리 순서에 잠재 위험이 있었다.** 루프가 `IAMFullAccess`를 4번째로 떼는데,
**그 순간 이후의 `DetachUserPolicy` 권한이 사라진다.** 뒤의 3개가 성공한 것은
**IAM 전파 지연 덕분이지 설계가 옳아서가 아니다.** 전파가 빨랐으면 중간에 멈췄을 것이다.
→ **IAM 관련 정책을 마지막에 떼도록 정렬해야 한다** (미수정, 아래 남은 것 참조).

**(4) 남은 1개는 루트 콘솔이 필요하다.** 재시도가 `AccessDenied: iam:DetachUserPolicy`로
끝났다 — **자기제한이 설계대로 작동한다는 실증**이기도 하다. 다만 하필 남은 것이
Budgets Actions 정책이라 **예산 알람 1개를 위해 필요 이상으로 넓은 정책이 남았다.**
루트 콘솔에서 떼는 것을 남은 작업으로 기록한다.

### ⚠️ 이 목록이 완전하다는 보장은 없다

액션 목록은 **Terraform 구성에서 역산한 것**이고, `plan`은 읽기만 한다.
**`plan` 통과가 `apply`/`destroy` 통과를 보장하지 않는다** — 세션 7이 "validate 통과 ≠
apply 통과"로 겪은 것과 같은 클래스의 문제다. 다음 배포·철거 때 드러난다.

## 4. 비용 · 지연 재측정 — 인젝션 방어의 실제 가격표

세션 5부터 세 세션을 이월해 온 항목이다. README §4가 `PROMPT_VERSION=2026-09-15.1`
기준이라 현재 코드와 직접 비교가 안 됐다.

**방법론은 세션 4와 동일하게 유지했다** (`docs/governance.md` "측정 방법론"):
임베딩 워밍업 분리, `LLM_CACHE` 꺼짐 확인 후 측정, 같은 머신·같은 코퍼스·같은 파라미터.
**바뀐 변수는 `PROMPT_VERSION` 하나다.**

> **컨테이너가 아니라 호스트에서 쟀다.** 세션 6은 "컨테이너 안에서 재는 것이 맞다"고
> 남겼지만, 이번 목적은 **프롬프트 버전 차이를 분리하는 것**이다. 환경까지 같이 바꾸면
> 토큰 증가가 방어 때문인지 환경 때문인지 갈리지 않는다. **환경 비교는 별도 과제다.**

### 결과 (n=9, 캐시 OFF)

| 지표 | `2026-09-15.1` | `2026-09-16.1` | 변화 |
| --- | ---: | ---: | ---: |
| 입력 토큰 합 | 92,299 | 119,535 | **+29.5%** |
| 출력 토큰 합 | 7,557 | 7,473 | −1.1% |
| **청구 토큰 / 요청** | 11,095 | **14,112** | **+27.2%** |
| LLM 지연 평균 | 15.762s | 15.648s | −0.7% |
| LLM 지연 p95 | 26.528s | 27.279s | +2.8% |
| 파이프라인 지연 평균 | 17.429s | 17.457s | +0.2% |
| **채점** | 8 pass / 1 fail | **8 pass / 1 fail** (동일 GS-006) | 동일 |

**결론 세 줄.**

1. **방어는 토큰으로 값을 치르고 지연으로는 치르지 않는다.** 입력이 30% 길어졌는데 지연은
   잡음 범위 안이다. 이 엔드포인트에서 지연을 지배하는 것은 입력 길이가 아니라 **출력 토큰 수**다.
2. **품질은 변하지 않았다.** 실패 케이스까지 같다. **출력을 바꾸지 않으면서 토큰만 27% 더 쓴다.**
3. **증가분의 2/3가 Researcher다** (18,113 / 27,236). `wrap_untrusted`가 스니펫마다 붙기
   때문이고, **Outliner만 증가가 0이다** — 이 노드만 검색 결과를 받지 않는다.
   ⚠️ **`top_k`를 올리면 방어 비용도 비례해 오른다.**

⚠️ **검색 지연 0.477s → 0.216s는 방어의 효과가 아니다.** 임베딩 웜 인코딩이
88.75ms → 29.27ms로 줄어든 머신 상태 차이다. 프롬프트는 검색 경로를 지나지 않는다.
**이 값을 개선 근거로 인용하면 안 된다.**

| 조건 | 파이프라인 평균 | 청구 토큰/요청 | 적중 | 채점 |
| --- | ---: | ---: | ---: | ---: |
| OFF | 17.457s | 14,112 | 0 / 108 | 8/9 |

### 4.1 `max_revisions=0` 대조 — **추정이 실측으로 바뀌었다** (ADR-006 Amendment)

세션 4가 "`max_revisions=0`이 지배적으로 낫다"고 적은 것은 **"재검색이 새 근거를 못
만든다"는 관찰에서 나온 추론**이었지 대조 측정이 아니었다. 이번에 직접 껐다.

| 지표 (n=9, 캐시 OFF) | `=2` | `=0` | 변화 |
| --- | ---: | ---: | ---: |
| **청구 토큰 / 요청** | 14,112 | **9,029** | **−36.0%** |
| LLM 호출 수 | 108 | **70** | −35.2% |
| 파이프라인 지연 평균 | 17.457s | **12.740s** | **−27.0%** |
| 파이프라인 지연 p95 | 37.430s | 27.064s | −27.7% |
| 채점 | 8 / 1 | **8 / 1** | 동일 |

**합계보다 케이스별 대조가 결정적이다. 9건 전부에서 인용 문서 ID·`uncovered_count`·
판정 체크가 완전히 일치했다.** Writer가 받는 입력 토큰도 양쪽 8,582로 같다.
**즉 근거를 하나도 잃지 않는다.**

**그래도 기본값을 0으로 바꾸지 않았다.** 바꾸면 되돌림 경로가 죽은 코드가 된다. 이 루프는
ADR-006의 핵심 결정을 구현하는 장치이고, 질의 재작성이 붙는 순간 값을 한다.
**"루프가 쓸모없다"가 아니라 "입력을 바꾸지 않는 루프가 쓸모없다"**이므로, 고칠 곳은
파라미터가 아니라 검색어 생성(`f"{query} {topic}"` 고정)이다.

**이 표가 질의 재작성의 허들이 된다** — 재작성이 값을 하려면 **토큰 36%·지연 27%를 더
쓰고도 근거를 늘려야 한다.**

⚠️ **코퍼스 16건 조건이다.** 코퍼스가 커지면 재검색이 새 문서를 물어올 여지가 생긴다.
ADR-006 Review Trigger를 그 조건으로 갱신했다.

| **Langfuse SDK 스팬 컨텍스트 경고** | 데이터는 전부 도착한다. 표시 문제로 보이나 미확인. ADR-016으로 클라우드 경로에서는 마주치지 않는다 — **해결이 아니라 회피다.** |

## 주의 (이월, 여전히 유효)

- 코드 실행은 **레포 루트를 cwd로**.
- **`aws` 명령은 에이전트가 실행할 수 없다** (`permissions.deny`). 사람이 `!`로 직접 친다.
  **`infra/iam/apply_least_privilege.sh`도 같다.**
- 지연 측정 전 **`LLM_CACHE` 상태 확인**, **임베딩 콜드 로딩 분리**.
- **호스트 / 컨테이너 / Fargate 수치를 직접 비교하지 말 것.** 셋 다 조건이 다르다.
- 인덱스·트레이스·캐시는 커밋하지 않는다. **클라우드에서는 EFS에 있다** —
  이미지를 지워도, 태스크 정의를 지워도 남는다. `terraform destroy`가 **데이터째** 지운다.
- 임베딩 모델을 바꾸면 `build_index.py --reset` **+ `EMBEDDING_REVISION` 설정**.
- **모델이 바뀌면 캐시를 비울 것.** `endpoint_fp`로 엔드포인트 변경을 확인할 수 있다.
- **Python 3.14 + Pydantic V1:** langfuse가 먼저 깨질 가능성이 높다. 이번 세션에도
  **새 의존성을 설치하지 않았다.**
