# Session 04 핸드오프 — 비용·지연 실측 + 캐시 + README 아키텍처 문서화 + v1.0

- **날짜:** 2026-09-15
- **범위:** 골든셋 재실행, 지연·토큰 실측(임베딩 로딩 분리), LLM 응답 캐시 도입,
  캐싱 전후 비교, README를 아키텍처 문서로 재작성, v1.0 태그
- **신규 ADR:** ADR-008. ADR-003 / ADR-006에 Amendment 추가.
- **태그:** `v1.0`

## 이번 세션의 핵심 변화

**측정 가능한 상태가 됐다.** session-03까지는 "돈다"였고, 이번에는 **얼마나 걸리고
얼마를 쓰는지, 그리고 무엇이 안 되는지**가 숫자로 나온다. 골든셋 9건이 자동 채점되고
(8 pass / 1 fail), 지연·토큰이 조건별로 비교된다.

**그 과정에서 재검색 루프가 실효성 없음이 확정됐다.** session-03의 의심이 골든셋 전체
측정으로 확인됐다 — 재검색이 Researcher 호출의 37%를 쓰면서 **새 근거를 하나도 만들지
못한다.** 이번 세션에서 고치지 않고 **알려진 한계로 정직하게 기록**했다.

### B. 코드

- `src/providers/cache.py` — `CachingLLMProvider`. `LLMProvider` 프로토콜을 그대로
  구현하는 데코레이터라 **노드 코드를 한 줄도 고치지 않고** 붙었다. 프로바이더 계층을
  둔 이유가 실제로 동작한다는 증거다. 디스크 기반(세션을 넘어 산다),
  `temperature > 0`은 캐시하지 않는다(샘플링 다양성을 조용히 없애지 않는다).
- `LLMResponse.cached` / `origin_latency_s` / `billed_tokens` — 비용 집계가
  "요청이 요구한 토큰"과 "실제로 청구된 토큰"을 구분해 세게 한다.
- `LLMCallRecord.cached` — 감사 로그가 캐시 적중을 구분해 기록한다.
- **`Finding.revision`** — 근거가 만들어진 회차. 재검색이 **새** 근거를 찾았는지
  자동 판정하기 위해 추가했다. session-03에서는 로그를 손으로 대조해야 했다.
- `scripts/bench_golden.py` — 골든셋 벤치마크. **임베딩 모델을 먼저 워밍업해
  상주시킨 뒤** 9건을 연속 실행한다. LLM 지연 / 검색 지연 / 전체 파이프라인 지연을
  분리 기록하고, 채점·재검색 실효성·캐시 통계를 JSON으로 남긴다.
- **테스트 67 → 78개** (캐시 11건 추가). 기존 67개 전부 그대로 통과.

### C. 실측 (n=9, 코퍼스 16건, 상주 프로세스)

원자료 `docs/eval/bench-*.json`, 해설 `docs/eval/run-log-session-04.md`.

**임베딩 로딩 분리** — session-03 "주의" 항목의 숙제를 처리했다:

| | 값 | 지연 수치 포함 |
| --- | ---: | --- |
| 임베딩 콜드 로딩 (기동 1회) | 19.4 ~ 30.2s (n=3) | **미포함** |
| 임베딩 웜 인코딩 (질의 1건) | 21 ~ 89ms | 포함 |

**지연:**

| 지표 | 평균 | p95 (n=9, nearest-rank) |
| --- | ---: | ---: |
| LLM 호출 지연 | 15.76s | 26.53s |
| 검색 지연 | 0.48s | — |
| 전체 파이프라인 (임베딩 포함) | 17.43s | 37.29s |

LLM이 파이프라인의 **90.4%**. 단계별로는 **토큰은 Researcher(67.6%), 지연은
Writer(32.0%)** 가 지배한다.

**캐싱 전후:**

| 조건 | 평균 지연 | 비용/요청 | 채점 |
| --- | ---: | ---: | ---: |
| 캐시 OFF | 17.43s | 11,095 토큰 | 8/9 |
| 캐시 ON (콜드) | 14.36s (−17.6%) | 10,069 토큰 (−9.2%) | 8/9 |
| 캐시 ON (웜) | 0.36s (−97.9%) | 0 토큰 (−100%) | 8/9 |

세 조건 채점이 동일 — **캐시가 출력을 바꾸지 않는다.**

**비용은 금액이 아니라 토큰으로 센다.** 현 엔드포인트가 무료 할당 자원이라 실제 금전
비용은 0원이고, 금액을 지어내 적으면 근거 없는 숫자가 문서에 남기 때문이다.

## 열린 이슈 / 결정 대기

### 막힌 것

- **arXiv가 여전히 429다.** session-03부터 session-04 종료 시점까지 계속 막혀 있다.
  **식별 가능한 User-Agent는 이미 설정돼 있어**(`scripts/ingest_corpus.py`) 헤더 누락이
  원인이 아님을 확인했다 — 단발 프로브도 즉시 `Rate exceeded`다. **몇 시간 뒤(또는 다른
  네트워크에서) 재시도가 필요하다.** 재시도 횟수를 늘리는 것은 해결책이 아니다.
  스크립트는 재개 가능하므로 그냥 다시 돌리면 남은 3개 주제
  (`verification-loop`, `rag-attribution`, `agent-orchestration`)를 이어받는다.
- **코퍼스 16건, `news` 출처 비어 있음.** 이번 세션의 모든 수치는 이 조건 기준이다.
  코퍼스가 늘면 커버리지·토큰이 함께 바뀌므로 **재측정이 필요하다**
  (`bench_golden.py`로 명령 한 줄이면 된다).

### 새로 드러난 것

- **GS-006 실패는 코퍼스 부족이 아니라 검색 재현율 문제다.** 기대 문서
  `arXiv:2404.01023v1`(*Large Language Model Evaluation Via Multi AI Agents*)이
  **코퍼스에 실제로 존재하는데도** 4개 항목 전부 "근거 없음"으로 끝났다. 제목이 질의와
  거의 같은 문서조차 통과하지 못한 것이다. session-03의 "코퍼스가 작아서 근거 없음이
  많다" 가설은 **이 케이스에 한해 기각된다.**
- **빈 캐시에서도 17/109(15.6%)가 적중했다.** 파이프라인이 글자 단위로 동일한 프롬프트를
  반복 전송한다는 직접 증거다.
- **재검색 루프를 끄는 것(`max_revisions=0`)이 현재 측정상 지배적으로 낫다.** 근거를
  하나도 잃지 않으면서 Researcher 호출 37%를 줄인다. 질의 재작성을 붙이기 전에 이것부터
  비교할 것.

### 계속 열려 있는 것 (session-03에서 이월)

- **사내 보안 정책상 무인증 엔드포인트 사용이 허용되는지 미확인.** ADR-004로 당장의
  위험은 피했지만 질문 자체는 남아 있다. **다음 세션이 보안이라면 이게 1순위다.**
- **2026년 말 대체 서빙 경로 미확보.** 전환 *비용*은 낮춰뒀지만 경로 자체가 없다.
  만료가 다가올수록 선택지가 줄어든다.
- **Langfuse self-host 미기동** — `LangfuseTracer` 경로 미검증.
- **체크포인터 백엔드 미선택** — 중단·재개 테스트 미실시 (ADR-002에서 계속 미완).
- 감사 로그 보존 기간·접근 권한 요구사항 — 로컬 JSONL에는 이 개념이 없다.
- 골든셋 `must_mention`(의미 판정)은 자동화하지 않았다. LLM 심판을 쓰면 판정 모델이
  또 하나의 변수가 되어 모델 고정 원칙과 충돌한다.
- `min_citations=1` / `max_revisions=2` / `top_k=4` — 여전히 근거 없이 정한 출발점.
  이제 골든셋이 있으니 비교할 수 있다.

## 다음 세션(보안) 전에 알아야 할 것

1. **무인증 엔드포인트 문제가 이 프로젝트의 가장 큰 미해결 보안 이슈다.** URL이 곧
   접근 권한이고, 우리는 엔드포인트 소유자가 아니라 IP 화이트리스트나 API 키를 추가할
   수 없다. 통제 가능한 지점은 "URL을 어떻게 다루는가"뿐이다 (README §7).
   **사내 정책상 이 상태가 허용되는지 확인**이 실질적인 첫 과제다.
2. **캐시가 새로운 데이터 표면을 만들었다.** `var/llm_cache/`에 프롬프트 해시와 **응답
   본문**이 평문 JSON으로 쌓인다. `var/`는 `.gitignore` 대상이라 커밋되지는 않지만,
   **디스크에 남는 내용물 관점에서는 새로 생긴 저장소다.** 현재는 공개 arXiv 초록만
   다루므로 문제가 없지만(ADR-004), 보존 기간·접근 권한을 볼 때 `var/traces/`와 함께
   다뤄야 한다.
3. **커밋 전 시크릿 검사는 `docs/governance.md`의 명령을 그대로 쓴다.** URL 조각을
   검사 명령에 직접 적지 않는다 — 그 자체가 평문 노출이다. 이번 세션에서도 실행했고
   출력은 비어 있었다.
4. **`.env`에 `LLM_CACHE=1`을 남겨두고 잊지 말 것.** 켜진 채로 측정하면 파이프라인
   성능이 아니라 캐시 적중률을 재게 된다. 기본값이 꺼짐인 이유이고, 벤치마크 스크립트가
   조건을 출력·기록하는 이유다.
5. **보안 관련 규칙을 새로 정하면 `docs/governance.md`에 쓴다.** `CLAUDE.md`는
   `.gitignore` 대상이라 팀에 전달되지 않는다. `.claude/rules/security.md`도 있다.

## 주의 (session-03에서 유효한 채로 이월)

- **지연을 잴 때 임베딩 로딩을 분리할 것.** 이번 세션의 `bench_golden.py`가 그 방식이다.
  `run_research.py`(질의 1건 = 프로세스 1건)로 잰 벽시계는 로딩이 섞여 있다.
- 코드 실행은 **레포 루트를 cwd로** 한다.
- 인덱스(`var/chroma/`), 계측 로그(`var/traces/`), 캐시(`var/llm_cache/`)는 커밋하지
  않는다. 재현의 기준은 **`data/corpus/` 스냅샷 + 임베딩 모델 이름**이다.
- 임베딩 모델을 바꾸면 `python scripts/build_index.py --reset`이 필요하다.
- **모델이 바뀌면 캐시를 비울 것** (`clear_cache`). 캐시 키에 모델 이름은 들어가지만,
  같은 이름으로 vLLM이 재배포되어 동작이 바뀌는 경우는 키에 잡히지 않는다.
- **Python 3.14 + Pydantic V1:** 현재 경고를 내는 것은 langchain-core와 langfuse다.
  실제 오류가 될 때는 **langfuse가 먼저 깨질 가능성이 높다**(임포트 시점에
  `pydantic.v1.datetime_parse`를 실제로 사용). 이번 세션에 pydantic을 새로 도입하지
  않았다 — 캐시는 표준 라이브러리만 쓴다.
