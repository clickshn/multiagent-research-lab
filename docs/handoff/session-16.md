# 파트 1 — 중복 upsert 방어 (session-15 §7.1(4) 종료)

## 1.1 무엇을 넣었나 — 두 형태 **둘 다**

session-15는 "거부 / 사후 검사 중 하나 또는 둘 다"로 열어뒀다. **둘 다 넣었고, 이유는
둘이 서로 다른 것을 보기 때문이다.**

| | 보는 것 | 못 보는 것 |
|---|---|---|
| **거부(사전)** | 이번 쓰기가 만들 중복 | 이미 들어 있던 중복, 이 스크립트 밖의 쓰기 |
| **사후 검사** | 인덱스의 **상태** (문서당 1행인가) | 아무것도 못 막는다 — 이미 쓴 뒤다 |

**사후 검사만으로는 방어가 아니다.** 알려주는 시점에 인덱스는 이미 결함 상태이고 남는
선택지는 `--reset`뿐이다. "감지했는데 이미 망가뜨렸다"는 사후 통보지 방어가 아니다.

### `--only-new` — 거부가 막아서는 안 되는 경로

거부만 넣으면 **코퍼스 증분 추가가 막힌다.** 실제로 20 → 37건으로 자란 경로가 바로
"`--reset` 없이 다시 돌리기"였다(그래서 결함이 생겼다). 정상 경로를 없애면 사람이
`--reset`을 습관화하고, 코퍼스가 커지면 결국 우회한다.

- `--reset`과 `--only-new`는 **함께 쓸 수 없다.**
- **`--reset`은 더러운 로그 위에서도 허용된다.** 유일한 복구 경로를 사전 검사가 막으면
  막다른 골목이 된다 — **이 구멍은 테스트가 먼저 잡았다.**
- ⚠️ `--only-new`는 **기존 문서의 본문이 바뀐 경우를 반영하지 못한다.** 같은 ID는 건너뛰므로
  인덱스가 조용히 낡는다. 스냅샷을 고쳤으면 `--reset`이다.

## 1.2 파일

- **`src/tools/index_guard.py` (신규)** — Chroma의 `embeddings_queue`·`embeddings`를
  **읽기 전용 sqlite**로 본다. 공개 API에는 쓰기 로그를 볼 수단이 없다.
  읽기 전용인 이유는 session-15 §4.3이다 — 질의가 인덱스 파일을 변형시키므로 검사 경로만큼은
  쓰기 가능성을 URI 수준에서 없앤다.
- **`scripts/build_index.py`** — 사전 거부 + 사후 검사. 종료 코드 분리
  (0 정상 / 1 코퍼스 없음 / **2 중복 upsert 거부** / **3 무결성 검사 실패**).
- **`src/tools/retrieval.py` — 파트 1에서 변경 0줄.** (파트 2에서는 additive로 바뀐다, §2.2)
- **`tests/test_index_guard.py` (신규, 12건)** — 임베딩 모델을 띄우지 않는다. **3.6s.**

> **검사 불가는 통과가 아니다.** Chroma 내부 테이블이 없으면 "이상 없음"이 아니라 예외다.
> 검사기가 고장 났는데 통과가 나오는 것은 검사가 없는 것보다 나쁘다 — 게이트가 통과했는데
> 게이트가 확인해야 할 것을 확인하지 않았던 ADR-021과 같은 형태다.

## 1.3 뚫어본 결과 (실제 코퍼스 37건, 인덱스 **사본**에서)

| 실행 | 결과 | `embeddings_queue` |
|---|---|---:|
| `--reset` 없이 2회차 | **거부 (exit 2)** | 37 → **37** (한 행도 쓰지 않음) |
| `--only-new` (새 문서 0건) | 통과 (exit 0), 인덱싱 건너뜀 | 37 |
| `--reset` | 통과 (exit 0), 37건 재인덱싱 17.4s | 37 |

테스트는 같은 절차를 격리 환경에서 재현한다. **종료 코드만 보지 않는다 — 쓰기 로그 행 수가
그대로인지까지 확인한다.** 거부가 쓰기 뒤에 일어나면 의미가 없기 때문이다.

**검사기의 양성 대조도 함께 둔다:** 방어를 우회해 문서당 2행 상태를 만들고 검사기가 실제로
잡는지 본다. "0건 검출"은 검사기가 고장 나도 똑같이 나오는 결과이기 때문이다
(`scripts/scan_local_secrets.py`와 같은 원칙).

**ID 규칙 이중화를 테스트가 붙든다.** 거부는 `build_index.index_id()`가 만든 ID로 판정하는데
같은 규칙이 `ChromaRetriever.index()`에도 있다. 갈리면 "겹치는 ID가 하나도 없다"로 보여
**거부가 조용히 무력해진다.** 실제 인덱싱 후 양쪽을 대조하는 테스트를 뒀다.

## 1.4 파트 1에서 **하지 않은 것**

- **운영 경로(`src/tools/retrieval.py`) 2차 방어 — 여전히 미결.** 다만 선택지가 하나 늘었다:

  session-15가 지적한 `top_k=4` 제약도 받지 않는다. **다음 세션의 결정 항목.**
- 재생 메커니즘 규명 — 안 했다. 방아쇠를 막았을 뿐 **메커니즘은 여전히 모른다.**
- `hnsw:search_ef` 확인 — 안 했다.
- ADR-012 재검토 조건 편입 — 안 했다.

# 파트 2 — 인용에 온톨로지 메타데이터 부착 (ADR-024)

## 2.1 범위를 먼저 정정했다

**"어떤 필터로 좁혔는가"를 인용에 남기는 것은 이번 범위가 아니다.** 선행 조건 둘이 없다:

1. 파이프라인에 **필터가 배선돼 있지 않다** — Session 3의 필터는 `probe_retrieval.py`의
   후처리다 (ADR-023).
2. 질의에서 필터 값을 고르는 **플래너가 없다** — Session 3이 쓴 것은 앵커에서 유도한 오라클이다.

→ **v1.2 항목으로 이월** (§3.1).

이번 범위는 **검색된 문서의 온톨로지 메타(`release_type` / `tech_domains` / 발행일)를
State를 통해 Writer 단계까지 보내고 인용에 붙이는 것**이다.

## 2.2 핵심 설계 — 메타는 **모델을 통과하지 않는다** (ADR-024)

**온톨로지 메타는 Writer의 LLM 입력(근거 블록)에 넣지 않는다. 코드가 렌더링하는 출처 표에만
붙는다.** 이유 셋:

1. **옮겨 적기는 틀릴 수 있다.** 모델이 `Community`를 `Paper`로 쓰면 감사 가능성이 모델
   정확도에 걸린다. 값은 검색 결과에 **이미 정확히 있다** — ADR-006의 "셀 수 있는 것은
   모델에게 묻지 않는다"와 같은 원칙이다.
2. **`release_type`을 Writer가 보면 근거 신뢰도 신호로 읽는다.** Researcher 프롬프트의
   유사도 점수 노출(§결정 대기 ①)과 **같은 함정**이다. 같은 실수를 인용 경로에서 반복하지 않는다.
3. **LLM 입력이 그대로면 `PROMPT_VERSION`이 안 바뀐다.** 그래야 "인용 형식 하나만 바뀌었다"가
   **정확히** 참이 되고 전/후 비교가 성립한다. → `PROMPT_VERSION = 2026-09-16.1` **그대로**.

## 2.3 메타 결측(층 B)의 표기 — **빈칸으로 두지 않는다**

`release_type`이 비는 이유는 **두 가지**이고 둘은 다른 사실이다.

| 상태 | 표기 | 뜻 |
|---|---|---|
| export를 거쳤고 값이 있다 | `Paper` | 확인된 값 |
| export를 거쳤는데 값이 비었다 | `없음` | 확인했고, 해당 없음 |
| **export를 거치지 않았다** | **`미확인`** | **확인 자체가 되지 않았다** |

셋째가 ADR-022의 **층 B**(스냅샷 arXiv 14/37건 = 37.8%)다. 빈칸 하나로 합치면 독자가
"등급이 없는 문서"와 "등급을 아직 모르는 문서"를 구별할 수 없고, **그 구별이 ADR-022가 층을
나눈 이유 그 자체다.**

판정 근거는 `has_ontology` — Chroma 메타의 `export_id` 유무다.

> **발행일은 두 층 모두 있다.** 스냅샷에도 `published`가 실려 있다. 즉 결측은 "이 문서를
> 모른다"가 아니라 **"온톨로지 라벨링을 거치지 않았다"**는 뜻이고, 표기도 그 범위에서만
> `미확인`이다. 발행일이 실제로 비면 그건 `없음`이다.

## 2.4 검색 결과가 바뀌지 않았다는 확인 (지시사항)

`RetrievedChunk` 확장은 **additive**다 — 질의·`where` 절·`k`·정렬·점수 계산은 한 줄도
바뀌지 않았다. 변경 **전/후**로 `probe_retrieval.py`를 같은 인덱스에서 각각 1회 돌려 대조했다.

```
python scripts/compare_probe_runs.py \
  docs/eval/probe-retrieval-session-16-before-chunk-metadata.json \
  docs/eval/probe-retrieval-session-16-after-chunk-metadata.json
```

**30케이스 전 필드가 시간 값을 제외하고 바이트 단위로 동일하다** —
양쪽 `sha256:00f6353bcd683bce…`. 차이가 난 유일한 키는 `retrieval_latency_s`(벽시계)였다.

- 🔧 **`scripts/compare_probe_runs.py` (신규)** — 제외 목록(`VOLATILE_KEYS`)을 **코드에 고정**한다.
  비교할 때마다 손으로 고르면 "이번엔 이것도 달라도 괜찮다"가 슬금슬금 늘어난다.
  제외는 **시간 값과 라벨뿐**이고, 문서 ID·순위·점수·재현율은 하나도 제외되지 않는다.

## 2.5 전/후 비교 — 출처 표의 결정론적 렌더링 대조 (**LLM 호출 0건**)

🔧 **`scripts/probe_citation_format.py` (신규)** → `docs/eval/citation-format-session-16.md`

| 케이스 | 층 | 메타 보유 | `미확인`(층 B) | LLM 입력 |

  있는지부터 판단**한 뒤 굳힌다. 바꾸지 않는다고 판단되면 굳혀도 된다.

## 4. 승인 게이트

- **LLM 호출 0건.** 게이트 양식 6항목을 제시했고, 사용자가 **"LLM 호출 0건으로 간다"**로
  범위를 정했다. `.claude/external-llm-approved`는 만들지 않았다(대상이 아니다).
- 유료 리소스 생성 0건, IaC 상태 변경 0건.
- 인덱스 조작은 **사본**(스크래치패드)에서만 했고 작업 후 삭제했다. `var/chroma`는
  `embeddings_queue` = 37 = 문서 수로 **깨끗한 상태 그대로**다.
