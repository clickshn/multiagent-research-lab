### 왜 상주 프로세스인가 — 임베딩 로딩을 분리한다

session-03의 측정은 질의 1건마다 프로세스를 새로 띄웠다. 그 방식에서는 임베딩 모델
첫 로딩(CPU, 수십 초)이 매 실행의 벽시계에 통째로 들어가 **"파이프라인이 느리다"와
"모델을 매번 새로 읽는다"가 구분되지 않는다** (session-03 실행 2: 벽시계 33.93s 중
LLM은 5.76s뿐).

이번에는 `_warm_up_embeddings()`로 모델을 먼저 상주시키고 그 시간을 따로 잰다.

| | 값 |
| --- | ---: |
| 임베딩 콜드 로딩 (기동 1회) | **19.4 ~ 30.2s** (3회 실행 관측 범위) |
| 임베딩 웜 인코딩 (질의 1건) | **21 ~ 89ms** |

**콜드 로딩은 아래 모든 지연 수치에 포함되지 않는다.** 상주 서비스로 배포하면
발생하지 않는 기동 1회 비용이기 때문이다. 이 값을 파이프라인 지연에 섞으면 모델이
실제보다 3배 느린 것처럼 보인다.

## 결과 1 — 지연 (캐시 OFF, n=9)

**"LLM 호출 지연"과 "전체 파이프라인 지연"을 분리해 적는다.**

| 지표 | 평균 | 중앙값 | p95 | 최대 |
| --- | ---: | ---: | ---: | ---: |
| **LLM 호출 지연** (모델 호출 합) | 15.76s | 16.62s | **26.53s** | 26.53s |
| **검색 지연** (임베딩 인코딩 + Chroma, 워밍업 후) | 0.48s | — | — | 0.78s |
| **전체 파이프라인 지연** (임베딩 포함, 콜드 로딩 제외) | 17.43s | 16.91s | **37.29s** | 37.29s |

- p95는 **nearest-rank**로 계산했다. n=9에서 보간하면 실제로 관측되지 않은 값이
  지표가 되므로, 항상 실측값을 돌려주는 방식을 썼다. n=9에서 p95는 사실상
  최댓값이므로 **"p95"라는 이름에 비해 안정성이 낮다** — 표본을 늘리기 전까지는
  범위 지표로 읽는 편이 정확하다.
- LLM이 파이프라인의 **90.4%** (15.76 / 17.43)를 차지한다. 나머지는 검색 0.48s와
  그래프·파싱 오버헤드 평균 1.19s다.

### "비용"을 토큰으로 세는 이유

현 엔드포인트는 **이미 할당된 무료 자원**이라 실제 금전 비용은 0원이다. 금액을 지어내
적으면 근거 없는 숫자가 문서에 남는다. 대신 **청구 토큰 수**로 센다 — 자원이 유료로
전환되거나 2026년 말 만료 후 대체 경로로 옮길 때(ADR-003) 그대로 금액으로 환산되는
단위이기 때문이다.

`billed_tokens`는 캐시 적중 호출을 0으로 센다. "요청이 요구한 토큰"과 "실제로 모델이
처리한 토큰"은 다른 수이고, 캐시 효과는 후자에서만 나타난다.

### 캐시가 비어 있는데 17건이 적중했다

`--clear-cache`로 캐시를 비우고 시작했는데도 **같은 실행 안에서** 17/109(15.6%)가
적중했다. 캐시 키는 프롬프트 본문의 해시이므로, 이것은 파이프라인이 **글자 단위로
동일한 프롬프트를 반복 전송**한다는 직접 증거다. 원인은 아래 재검색 루프다.

### 캐시가 출력을 바꾸지 않는다

세 조건 모두 채점 결과가 **8 pass / 1 fail로 동일**했다. 캐시가 품질에 영향을 주지
않는다는 것을 확인한 것이다 (ADR-008 AI/ML Details).

### GS-006 실패 — 코퍼스 부족이 아니라 검색 재현율 문제

> 질의: "LLM의 성능을 평가하기 위해 멀티에이전트 구조를 사용하는 접근이 있는가?"
> 기대 문서: `arXiv:2404.01023v1` — *Large Language Model Evaluation Via Multi AI Agents*

**기대 문서는 코퍼스에 실제로 존재한다** (`data/corpus/arxiv/agent-evaluation.json`에서
확인). 그런데도 4개 항목 전부 "근거 없음"으로 끝났고 인용이 0건이다.

즉 이 실패는 코퍼스가 작아서가 아니라, **제목이 질의와 거의 같은 문서조차 검색·판정
경로를 통과하지 못했다**는 뜻이다. 재검색 2회도 아무것도 바꾸지 못했다(위 결과 3).
이것이 다음 세션에서 `top_k`·청크 전략·질의 재작성을 봐야 할 가장 구체적인 근거다.

session-03의 "코퍼스가 작아서 근거 없음이 실제보다 많이 나올 수 있다"는 가설은
**이 케이스에 한해서는 기각된다.** 다른 케이스에도 해당하는지는 코퍼스를 채운 뒤에야
갈린다.

## 재현 방법

```bash
python scripts/build_index.py            # 인덱스가 없으면
python scripts/bench_golden.py --label no-cache --clear-cache
python scripts/bench_golden.py --label cache-cold --cache --clear-cache
python scripts/bench_golden.py --label cached --cache     # 위 실행이 채운 캐시 사용
```

주의: `--label cached`는 **직전 실행이 캐시를 채워둔 상태**를 전제한다. 빈 캐시에서
돌리면 `cache-cold` 조건이 된다.

## 계측 백엔드에 대한 사실 정정

이번 세션의 수치는 **Langfuse가 아니라 로컬 JSONL 트레이스**에서 나왔다.
`.env`에 Langfuse 자격증명이 없어 `LangfuseTracer`가 활성화되지 않기 때문이다
(`TracingSettings.langfuse_enabled == False`).

계측 파사드(ADR-007)를 둔 덕분에 **같은 데이터가 같은 구조(trace 1개 = 실행 1건,
span 1개 = 호출 1건)로 남았고**, Langfuse 서버를 붙이면 코드 변경 없이 동일한 span이
그쪽으로도 간다. 다만 `LangfuseTracer` 경로는 **여전히 실제 서버로 검증되지 않았다**
(session-03부터 이월된 미완 항목).
