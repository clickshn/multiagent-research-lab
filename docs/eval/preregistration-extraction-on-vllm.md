# 사전 등록 — 추출 단계를 KT Cloud vLLM으로 옮길 때의 판정 기준

- **등록일:** 2026-09-17 (session-11)
- **상태:** 등록 완료 / **미실행**
- **근거 ADR:** ADR-021(전제 위반과 게이트), ADR-002(모델 고정·vLLM 서빙)

> **데이터를 보기 전에 적는다.** 값을 보고 나서 기준을 정하면 그 기준은 결론을 따라간다.
> 이 문서를 커밋한 시점이 git 이력에 남는 것이 사전 등록의 실체다 — **실행 커밋보다
> 앞서 있어야 의미가 있다.**

---

## 1. 왜 옮기나 — 목적은 비용 절감이 아니다

**전제 위반 해소다.** ADR-002가 서빙을 vLLM(`gemma-4-31B-it`)으로 고정했는데
**코퍼스 생성만 외부 벤더를 쓰고 있다.** 같은 시스템의 입력을 만드는 단계가 다른 원칙
위에 있는 상태이고, Session 0.5a의 위반이 정확히 그 지점에서 났다 (ADR-021).

비용($2.13 → 0)은 부수 효과다. **비용을 이유로 적으면 판정 기준이 흔들린다** —
"품질이 좀 떨어져도 싸니까"가 들어올 자리가 생긴다. 여기서 재는 것은 **전제를 지키면서
계약을 만족할 수 있는가**이고, 못 하면 그때는 조직 결정으로 올린다(§5).

## 2. 대조 설계 — 추가 비용 0

- **입력을 새로 만들지 않는다.** 이미 Opus 5로 뽑은 **30건과 동일한 입력**
  (같은 본문·같은 프롬프트 v4·같은 스키마)을 vLLM으로 다시 돌린다.
  생산자 보존소에 원문이 남아 있으므로(생산자 ADR-015: 변환 전에 API 결과를 먼저 저장)
  **수집을 다시 하지 않고, 외부 API를 한 번도 더 부르지 않는다.**
- 따라서 **추가 비용은 0**이고, 대조는 "같은 입력 · 다른 모델"의 단일 변수 비교가 된다
  (ADR-002의 "한 번에 하나만 바꾼다").

### 2.1 대조가 성립하려면 — 먼저 확인할 것

| # | 확인 | 성립하지 않으면 |
|---|---|---|
| 1 | 프롬프트를 **한 글자도 바꾸지 않고** 돌릴 수 있는가 | gemma에 맞춰 프롬프트를 고치면 변수가 둘이 된다. 고쳐야 한다면 **그 사실을 결과에 적고** "모델 교체"가 아니라 "모델+프롬프트 교체"로 부른다 |
| 2 | structured output(스키마 강제)을 vLLM에서 **같은 강도로** 걸 수 있는가 | vLLM의 guided decoding과 벤더 structured outputs는 강제 수준이 다르다. 다르면 §3-(2)의 수치가 모델 능력이 아니라 **디코딩 설정**을 재게 된다 |
| 3 | 재시도 정책이 같은가 (생산자 `SchemaMismatchError` 경로) | 재시도 횟수가 다르면 실패율이 비교 불가다 |
| 4 | `prompt_sha256`이 달라지는가 | 계약상 다른 추출이 된다. 달라지면 manifest에 그대로 기록한다 |

## 3. 판정 기준 — **이 값들은 지금 확정한다**

기계 판정 둘(①②)이 1순위이고, judge(③)는 **단독 판정 근거로 쓰지 않는다**(§3.3).

### ① 통제어휘 이탈률 — **≤ 5%**

- **정의:** 30건이 만든 온톨로지 값 중 **매 export manifest의 `vocab` 목록 밖**에 있는
  값의 비율. 분모는 값의 개수(레코드 수가 아니다), 분자는 목록 밖 값의 개수.
- **측정:** MARA의 `src/tools/contract_import.py` 어휘 대조(계약 §5)를 그대로 쓴다.
  **새 판정기를 만들지 않는다** — 판정기가 바뀌면 그것도 변수다.
- **Opus 5 기준선:** **0%** (계약 §12.2-10, 30줄 전 값이 `vocab` 안).
- **왜 0%가 아니라 5%인가:** 기준선이 0%라고 해서 합격선을 0%로 두면 **1건만 어긋나도
  탈락**이고, 그 1건이 모델 능력 차이인지 디코딩 설정 차이인지 구분되지 않는다.
  30건 × 7필드 기준으로 5%는 약 10개 값이다.

### ② structured output 실패율 — **≤ 10%**

- **정의:** 재시도까지 마친 뒤에도 스키마로 파싱되지 않아 **격리된 레코드**의 비율
  (생산자 `SchemaMismatchError`). 부분 통과는 실패로 센다.
- **Opus 5 기준선:** 생산자 session-01에 실패 기록이 없다 → **0건으로 본다.**
  ⚠️ **"기록이 없다"와 "0이었다"는 다르다.** 이전 시점에 실패가 기록되지 않았을
  가능성이 있으므로, 이전 실행 시 **양쪽 모두 실패 카운터를 남긴다.**
- 10% = 30건 중 3건. 이보다 나쁘면 코퍼스 생성이 파이프라인의 병목이 된다.

### ③ 골든셋 judge 점수 차이 — **평균 0.5점 이내 (1~5 척도)**

- **정의:** 생산자 `eval`의 `summary_faithfulness` 평균. 절대 임계값은 생산자 config의
  **4.0**이고, 여기서 보는 것은 **Opus 5 산출물과의 차이**다.
- ⚠️ **judge도 vLLM에서 돌려야 한다.** judge를 `claude-opus-5`로 두면
  **판정하는 행위 자체가 같은 위반이다**(생산자 `config.yaml`의 `eval.judge_model`이
  현재 그 값이다). 이 이전 작업에는 **judge 교체가 포함된다.**
- ⚠️ **judge와 후보가 같은 모델이 되면 자기 선호 편향이 생긴다.** gemma가 gemma의
  출력을 채점하게 되므로, 이 점수는 **참고값**이고 ①②가 갈리면 ①②를 따른다.

### 3.1 한 줄 요약 — 무엇이 합격인가

> **① ≤ 5% **그리고** ② ≤ 10%** 이면 합격. ③은 기록하되 단독으로 불합격을 만들지 않는다.

### 3.2 기준을 바꾸고 싶어지면

**데이터를 본 뒤에 임계값을 바꾸면 이 문서는 무효다.** 바꿔야 할 이유가 생기면
바꾸지 말고 **그 이유를 결과에 적는다.** 그것이 다음 사전 등록의 입력이 된다.

### 3.3 이 판정으로 재지 **않는** 것

- 지연·처리량. 프롬프트가 9,200토큰이라 vLLM 쪽이 느릴 수 있지만, **코퍼스 생성은
  오프라인 배치**라 질의 지연과 성질이 다르다. 재더라도 합격 기준에 넣지 않는다.
- 요약문의 "좋음". 인용 정확도는 원문 대조로 재고(ADR-006), 문장 품질은 이 이전의
  판단 대상이 아니다.

## 4. 실행 순서

> ⛔ **선행 조건: 생산자 레포에 게이트가 이식돼 있어야 한다** (session-11 §5).
> 아래 2·4번이 전부 그 레포에서 LLM을 호출하는 일이다. 장치 없이 시작하면
> **전제를 고치러 가는 작업 중에** 같은 위반이 난다.

1. §2.1의 네 항목을 먼저 확인하고 **결과를 적는다.** 여기서 갈리면 대조를 시작하지 않는다.
2. 동일 입력 30건을 vLLM으로 재추출. **외부 API 호출 0건**이어야 한다.
3. ①②를 MARA의 기존 판정기로 측정.
4. judge를 vLLM으로 바꾼 뒤 ③ 측정.
5. 결과를 `docs/eval/run-log-session-NN.md`에 남기고, 합격/불합격을 §3.1로 판정.

## 5. 판정 이후 — 미리 정해 둔다

| 결과 | 따라오는 것 |
|---|---|
| **합격** | 추출 경로를 vLLM으로 이전한다. **2단계 220건도 vLLM으로** 돌리므로 약 $16의 승인 자체가 없어진다. 생산자 `config.yaml`의 `llm.provider` 교체가 본 작업이 된다 |
| **불합격** | 전제와 품질이 충돌하는 것이 **측정으로 확인된** 상태다. 이때 비로소 "외부 벤더 사용을 승인할 것인가"를 **조직 결정**으로 올린다. 그 전까지 2단계 220건은 실행하지 않는다 (ADR-021) |

**불합격이 "외부 API를 써도 된다"를 뜻하지 않는다.** 판단 근거가 추정에서 측정으로
바뀔 뿐이고, 결정 주체는 여전히 사람이다.
