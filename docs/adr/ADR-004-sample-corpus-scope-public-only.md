# ADR-004: 샘플 코퍼스는 공개 자료로만 구성한다

- **Status:** Proposed
- **Date:** 2026-09-15
- **Decision:** 이 프로젝트의 VectorDB에는 공개 자료(arXiv 논문 초록, 공개 AI/기술 뉴스)만 넣고, 실제 사내 기밀 문서는 넣지 않는다.
- **Scope:** multiagent-research-lab (데이터 반입 범위 / 코퍼스)
- **Decision Source:** Human

---

## Context

### Problem

Researcher 노드를 구현하려면 검색 대상 코퍼스가 있어야 한다. 이 시스템이 상정하는
사용 맥락은 "사내 규정·기술 문서·과거 프로젝트 산출물을 근거로 조사 보고서를 쓰는
실무자"(`docs/problem-statement.md` §1)이므로, 자연스러운 다음 단계는 실제 사내
문서를 인덱싱하는 것이다.

그런데 session-02에서 서빙 경로의 실태가 확인됐다. 현재 추론에 쓰는 KT Cloud AI
Nexus vLLM 엔드포인트는 **인증을 요구하지 않고 어떤 네트워크에서든 접근 가능하다**
(`README.md` "보안 / 운영", `docs/governance.md`). 우리는 엔드포인트 소유자가 아니라
IP 화이트리스트나 API 키를 추가할 수 없고, 통제 수단은 URL을 시크릿으로 취급하는
것뿐이다.

이 상태에서 실제 사내 문서를 질의에 태우면, 문서 내용이 우리가 접근 통제를 걸 수
없는 엔드포인트로 전송된다. 이것은 코드로 해결할 문제가 아니라 회사 보안 정책의
검토가 필요한 문제이며, 개인 포트폴리오 프로젝트가 단독으로 결정할 사안이 아니다.

동시에, 코퍼스가 없으면 세션 3의 목표(sub-agent 구현 + e2e 동작 확인)가 통째로
막힌다. 코퍼스 종류를 정하는 것과 사내 문서 반입 여부를 정하는 것을 분리해야 한다.

### Constraints

- 엔드포인트가 무인증 공개 접근이라, 투입 데이터는 "외부에 노출돼도 문제없는 것"이어야 한다.
- 이 프로젝트가 실제로 검증하려는 것은 **하네스(오케스트레이션 구조·검증 루프·컨텍스트
  관리)가 결과 품질을 얼마나 좌우하는가**다. 코퍼스는 하네스를 돌리기 위한 입력이지
  검증 대상 자체가 아니다.
- 출처 제시가 1순위 제약이다 (`docs/problem-statement.md` §3 목표 2). 코퍼스는 문서 ID와
  문서 내 위치를 안정적으로 가질 수 있는 형태여야 한다.
- 재현성 요구가 있다. 같은 인덱스 스냅샷에서 같은 결과가 나와야 한다.

## Decision

### Selected

- **Technology:** arXiv API (공개 논문 메타데이터·초록), 공개 AI/기술 뉴스
- **Architecture:** 허용 출처를 `src/tools/corpus.py`의 `ALLOWED_SOURCES = ("arxiv", "news")`로 코드에 고정하고, 인덱싱·검색 경로가 이 화이트리스트를 강제한다. 허용 목록 밖의 출처는 빈 결과가 아니라 `CorpusScopeError` 예외다.
- **Implementation:** `scripts/ingest_corpus.py`가 arXiv API에서 초록을 수집해 `data/corpus/arxiv/*.json` 스냅샷으로 커밋한다. 인덱스(`var/chroma/`)는 커밋하지 않고 스냅샷에서 재생성한다 — 재현의 기준은 인덱스가 아니라 스냅샷 + 임베딩 모델 이름이다. `docs/problem-statement.md` §1에 범위 주의 문단을 추가해, 사내 문서 맥락이 "가정된 사용 맥락"이고 실제 투입 데이터는 공개 자료임을 명시했다.

## Rationale

1. **사내 문서 투입은 코드 결정이 아니라 보안 정책 결정이다.** 엔드포인트에 접근 통제를
   걸 수 없는 상태에서 사내 문서를 태우는 것은, 기술적으로 가능하더라도 회사 정책 검토를
   건너뛰는 일이 된다. 이 프로젝트의 범위를 벗어나므로 범위 밖이라고 명시적으로 기록한다.
2. **하네스 검증에는 공개 코퍼스로 충분하다.** 이 프로젝트가 알고 싶은 것은 오케스트레이션
   구조가 결과 품질을 얼마나 좌우하는가이지, 특정 문서 집합에서의 검색 성능이 아니다.
   코퍼스를 바꿔도 하네스 평가의 성격은 바뀌지 않는다.
3. **arXiv 초록은 출처 구조가 이미 갖춰져 있다.** 논문 ID가 안정적인 문서 ID가 되고,
   초록은 그 자체로 하나의 인용 단위다. 출처 제시 요구를 만족시키기 위해 별도의 청크
   경계 설계를 먼저 하지 않아도 된다.
4. **정책을 코드에 박아야 다음 세션에서 깨지지 않는다.** 문서에만 적어두면 몇 세션 뒤에
   무심코 사내 문서 디렉터리를 인덱싱하게 된다. 화이트리스트가 예외를 던지면 그 실수가
   즉시 실패로 드러난다.
5. **공개 코퍼스는 포트폴리오로서도 낫다.** 결과물과 실행 로그를 그대로 공유해도
   기밀 문제가 없다.

## Evidence

- **Experiment:** session-03 e2e 실행 — 공개 arXiv 초록 16건 인덱스에서 조사 항목 4개 중
  2개에 근거가 붙고 2개가 "근거 없음"으로 표시됐다 (run_id `20260915-152557-c34630`).
  코퍼스에 근거가 전혀 없는 질의로 돌렸을 때는 4개 항목 전부가 "근거 없음"으로 남고
  한 문장도 생성되지 않았다 (run_id `20260915-152711-81bcd7`). 근거 없는 항목을
  지어내지 않는다는 설계 원칙이 공개 코퍼스에서도 그대로 검증됐다.

## Alternatives

### 실제 사내 문서를 인덱싱

- **Pros:** 상정한 사용 맥락과 정확히 일치한다. 검색 품질·청크 전략을 실제 문서 형식에서 검증할 수 있다.
- **Cons:** 문서 내용이 무인증 공개 엔드포인트로 전송된다. 우리가 접근 통제를 추가할 수 없다.
- **Rejected because:** 회사 보안 정책 검토가 별도로 필요한 문제이고, 이 포트폴리오 프로젝트의 범위를 벗어난다.
- **Recheck if:** 사내 보안 정책상 현 엔드포인트로 사내 문서를 질의하는 것이 허용되는지 확인되고, 허용된다는 답을 받는 경우.

### 사내 문서를 익명화·마스킹해서 투입

- **Pros:** 실제 문서 형식을 유지하면서 민감 정보 노출을 줄인다.
- **Cons:** 마스킹이 충분한지 판단하는 것 자체가 보안 검토 대상이다. 불완전한 마스킹은 안전하다는 착각만 준다.
- **Rejected because:** 위험을 줄이는 게 아니라 위험 판단을 우리가 떠안는 선택이라, 범위 문제를 해결하지 못한다.

### 합성(생성) 문서로 코퍼스 구성

- **Pros:** 보안 문제가 전혀 없고, 원하는 형식으로 만들 수 있다.
- **Cons:** 내용이 실제가 아니라 근거 정확도를 평가할 기준이 되지 못한다. 골든셋의 "정답 근거"가 허구가 된다.
- **Rejected because:** 출처 제시 정확도가 이 프로젝트의 1순위 지표인데, 출처 자체가 지어낸 것이면 측정에 의미가 없다.

## Consequences

### Positive

- 실행 결과·로그·초안을 그대로 공유해도 기밀 문제가 없다.
- 코퍼스가 공개 API에서 재수집 가능해 재현성이 높다.
- 사내 문서 반입 여부라는 미해결 정책 문제가 코드 진행을 막지 않는다.

### Negative

- 실제 사내 문서의 형식(표, 스캔 PDF, 사내 용어)에서 오는 문제를 이 프로젝트에서는 만나지 못한다. 청크 전략·OCR·용어 사전 같은 이슈가 미검증으로 남는다.
- 한국어 문서 비중이 낮다. arXiv 초록은 대부분 영어라, 한국어 질의 + 영어 문서라는 교차 언어 검색 상황이 기본이 된다.

### Risks

- 이 프로젝트에서 검증된 검색 품질이 실제 사내 문서에서 그대로 재현되지 않을 수 있다. 하네스 구조에 대한 결론은 이전되지만 검색 성능 수치는 이전되지 않는다.
- 공개 뉴스 출처(`news`)는 화이트리스트에만 열어두고 아직 수집하지 않았다. 출처가 하나뿐이라 출처 다양성에서 오는 문제(형식 차이, 중복 문서)가 드러나지 않는다.
- arXiv가 이 IP를 429로 제한해 계획한 5개 주제 중 2개(16건)만 수집됐다. 코퍼스가 작아 "근거 없음"이 실제보다 많이 나올 수 있다 — 검증 루프의 판정 조건(ADR-006) 평가와 혼동하지 않아야 한다.

## Implementation

- [x] `ALLOWED_SOURCES` 화이트리스트와 `assert_allowed_source()` 강제 경로 (`src/tools/corpus.py`)
- [x] arXiv 수집 스크립트 (`scripts/ingest_corpus.py`) — 공개 API, 재개 가능
- [x] `docs/problem-statement.md` §1에 범위 주의 문단 추가
- [x] 화이트리스트 위반 테스트 (`tests/security/test_corpus_scope.py`)
- [ ] `news` 출처 수집 — 공개 AI/기술 뉴스 (다음 세션)

## Reversibility

- **Reversible:** Partial
- **Rollback:** 공개 코퍼스를 빼고 다른 코퍼스로 바꾸는 것은 스냅샷 교체 + 인덱스 재생성이라 비용이 낮다. 다만 **사내 문서를 넣는 방향으로 되돌리는 것**은 코드 변경이 아니라 회사 보안 정책 검토가 선행되어야 하므로, 우리 쪽 결정만으로는 되돌릴 수 없다.
- **Migration Cost:** Low (코퍼스 교체) / High (사내 문서 반입으로 전환)

## Review Trigger

- 사내 보안 정책상 현 무인증 엔드포인트로 사내 문서를 질의하는 것이 허용되는지 확인되고, 허용된다는 답을 받는 경우 — 사내 문서 인덱싱 재검토.
