# ADR-013: 배포 대상은 ECS Fargate (온디맨드 태스크)로 한다

- **Status:** Proposed
- **Date:** 2026-09-16
- **Decision:** ADR-010의 컨테이너 이미지를 AWS ECS Fargate에서 **온디맨드 태스크(`RunTask`)** 로 돌린다. App Runner와 EKS는 기각한다. 판단 기준은 비용(특히 안 쓸 때의 고정비), 운영 부담, 포트폴리오 가치다.
- **Scope:** multiagent-research-lab (배포 대상 / 세션 7)
- **Decision Source:** Human

---

## Context

### Problem

ADR-010에서 이미지가 만들어졌고 로컬 스택이 검증됐다. 세션 7에서 클라우드에 올려야 하는데
어디에 올릴지가 정해지지 않았다. 이것은 **새 유료 리소스 생성**이라 사전 승인 대상이고
(`docs/governance.md` "승인 게이트"), 근거를 남겨야 한다.

**Bedrock은 후보가 아니다.** 파운데이션 모델 서빙 서비스라 이미 KT Cloud AI Nexus로
해결된 부분과 겹치고(ADR-003), docker-compose 스택을 올리는 것과 무관하다. 우리가 배포하려는
것은 모델이 아니라 **오케스트레이터 컨테이너**다.

### Constraints

- **상시로 켜둘 필요가 없다.** 이 파이프라인은 요청-응답 서비스가 아니라 **작업 컨테이너**다.
  리서치 1회 = 프로세스 1회 = trace 1개 (ADR-007, ADR-010). 하루에 몇 번 돌 수도, 며칠 안 돌 수도 있다.
- **HTTP 서버가 없다.** `scripts/run_research.py`는 CLI다. 포트를 열지 않는다.
- **추론은 외부로 나간다.** 엔드포인트는 KT Cloud이고 AWS 안에 있지 않다 (ADR-003).
  따라서 아웃바운드 인터넷 경로가 필요하고, AWS 리전 선택이 추론 지연에 영향을 준다.
- **시크릿은 런타임 주입이어야 한다.** `VLLM_BASE`가 이미지에 들어가면 안 된다 (ADR-010).
- **이미지가 3.46GB다.** 콜드 스타트 시 이미지 풀 시간과 ECR 저장 비용에 영향을 준다.
- **복제본은 1개다.** Chroma 임베디드가 단일 프로세스를 전제하므로(ADR-012), 배포 형태가
  복제본을 늘리는 쪽이면 저장소 결정이 함께 깨진다.
- 이 프로젝트는 포트폴리오이기도 하다 — **컨테이너 오케스트레이션 경험이 드러나는 정도**가
  판단 기준에 포함된다.

## Decision

### Selected

- **Technology:** Amazon ECS + Fargate 시작 유형. **서비스(`desiredCount`)를 두지 않고**
  `RunTask`로 태스크를 1회 실행한다. 이미지는 ECR에, 로그는 CloudWatch Logs에.
- **Architecture:** 클러스터 1개 + 태스크 정의 1개. 상시 실행 컴포넌트가 없다.
  `VLLM_BASE`는 **태스크 정의의 `secrets`** 로 SSM Parameter Store(SecureString)에서 주입한다 —
  `environment`(평문)가 아니다. 태스크 정의는 `describe-task-definition`으로 누구나 읽힌다.
- **Implementation:** 세션 7에서 진행. 이번 세션은 **코드만 준비하고 apply하지 않는다.**
  Terraform 최소 구성(`infra/terraform/`)은 ECR 리포지토리와 CloudWatch 로그 그룹 2개뿐이며,
  둘 다 ECS의 선행 리소스이면서 유휴 비용이 사실상 0인 것들이다.

## Rationale

1. **안 쓸 때 고정비가 0에 수렴하는 유일한 후보다.** ECS 컨트롤플레인 자체가 무료이고,
   Fargate는 태스크가 도는 동안만 초당 과금한다. 서비스를 두지 않으면 **유휴 시 컴퓨트 비용이
   문자 그대로 0**이다. 남는 고정비는 ECR 이미지 저장 약 $0.35/월뿐이다.
2. **EKS는 조건과 정면으로 충돌한다.** 컨트롤플레인이 클러스터당 시간당 과금이라
   **아무것도 안 돌려도 월 ~$73**이다. "상시로 켜둘 필요 없음"이 이 프로젝트의 성질인데
   가장 큰 비용이 상시로 발생한다. 실행 비용(월 몇 달러 수준)보다 **고정비가 20배 이상 크다.**
3. **App Runner는 기각 사유가 비용보다 앞서 구조에 있다.** App Runner는 **HTTP 요청을 받는
   서비스**를 전제한다 — 포트를 열고 헬스체크에 응답해야 한다. 우리 오케스트레이터는 CLI
   작업 컨테이너다. 올리려면 **쓰지도 않을 웹 API를 감싸야 하고**, 그 순간 배포한 것이
   우리가 검증한 스택이 아니게 된다. 비용 면에서도 서비스가 살아 있는 동안 유휴 메모리가
   과금돼 "안 쓸 때 0"이 성립하지 않는다.
4. **포트폴리오 가치는 ECS Fargate가 중간이면서 정직하다.** 태스크 정의, 클러스터, IAM 태스크
   역할 / 실행 역할 분리, VPC·서브넷·보안그룹, ECR, CloudWatch 로그 — 컨테이너 오케스트레이션의
   실제 표면이 전부 드러난다. App Runner는 이걸 **감춰서** 보여줄 것이 없고, EKS는 더 많이
   보여주지만 **이 워크로드에 k8s가 필요했다는 근거가 없다** — 과잉 설계는 포트폴리오에서
   가산점이 아니라 판단력에 대한 감점이다. "왜 EKS가 아닌가"에 숫자로 답할 수 있는 편이 낫다.
5. **복제본 1개 모델과 맞는다.** 온디맨드 태스크는 본질적으로 1회 1개다. Chroma 임베디드의
   단일 프로세스 전제(ADR-012)를 깨지 않는다. 서비스형으로 갔다면 `desiredCount`를 늘리는
   순간 저장소 결정이 조용히 무효가 됐을 것이다.

## Alternatives

### AWS App Runner

- **Pros:** 운영 부담이 가장 낮다. 이미지만 주면 배포·스케일·TLS·도메인이 자동이다.
  ECR 푸시에 연동한 자동 재배포를 지원한다.
- **Cons:** **HTTP 요청을 받는 서비스가 전제다** — 포트를 열고 헬스체크에 응답해야 한다.
  우리 워크로드는 CLI 배치라 쓰지 않을 웹 계층을 새로 만들어야 하고, 그러면 배포된 것이
  검증한 스택과 달라진다. 서비스가 살아 있는 동안 유휴 메모리가 과금돼 "안 쓸 때 0"이
  성립하지 않는다. 오케스트레이션 세부를 감추므로 포트폴리오로 드러낼 표면도 가장 적다.
- **Rejected because:** 판단 기준 셋 중 어느 것도 이기지 못한다. 비용은 유휴 과금이 있어 지고,
  포트폴리오 가치는 가장 낮으며, 운영 부담이 낮다는 유일한 장점은 **애초에 맞지 않는 워크로드를
  억지로 맞춘 뒤에야** 얻어진다.
- **Recheck if:** 이 프로젝트에 실제로 HTTP API가 생기는 경우 (리서치를 외부에서 호출하는
  인터페이스를 만들게 되면 전제가 바뀐다).

### Amazon EKS

- **Pros:** 컨테이너 오케스트레이션 경험 노출이 가장 크다 — k8s 매니페스트, 스케줄링, HPA,
  네임스페이스 등. 벤더 종속이 가장 낮아 다른 클라우드나 온프렘으로 옮기기 쉽다.
  2026년 말 서빙 경로 전환(`CLAUDE.md`) 같은 이동성 요구에 유리하다.
- **Cons:** 컨트롤플레인 고정비가 클러스터당 월 ~$73이고 **아무것도 안 돌려도 발생한다.**
  노드 비용은 별도다. 운영 부담(버전 업그레이드, 애드온, IRSA 설정)이 세 후보 중 가장 크다.
  복제본 1개 워크로드에 k8s의 스케줄링 능력이 값을 하지 않는다.
- **Rejected because:** **"상시로 켜둘 필요 없음"이라는 이 워크로드의 핵심 성질과 고정비 구조가
  정면으로 충돌한다.** 월 100회 실행 비용이 ~$1.7인데 고정비가 $73이면 비용의 98%가 쓰지 않는
  시간에 대한 것이다. 오케스트레이션 노출이라는 이점은 실재하지만, **필요하지 않은 복잡도를
  샀다는 사실이 함께 드러난다.**
- **Recheck if:** 여러 워크로드가 한 클러스터를 공유해 고정비가 분산되는 경우, 또는 상시
  실행 컴포넌트가 생겨 고정비가 유휴 비용이 아니게 되는 경우.

### ECS EC2 시작 유형

- **Pros:** 장시간·고빈도 실행에서 Fargate보다 단가가 싸다. 인스턴스 타입을 직접 고른다.
- **Cons:** EC2 인스턴스를 상시로 띄워 두면 유휴 고정비가 생기고, 안 띄우면 Fargate와
  같은 온디맨드 모델이 되는데 인스턴스 기동 관리가 추가된다.
- **Rejected because:** 고정비 0이라는 이점을 잃거나, 유지하려면 관리 대상만 늘어난다.
  실행량이 적은 지금 단가 이득이 발생하지 않는다.

### Amazon Bedrock

- **Pros:** —
- **Cons:** 파운데이션 모델 서빙 서비스다. 컨테이너를 돌리는 서비스가 아니다.
- **Rejected because:** **후보가 아니다.** 이미 KT Cloud AI Nexus로 해결된 영역과 겹치고
  (ADR-003), docker-compose 스택을 올리는 문제와 무관하다. 게다가 외부 LLM 벤더 비의존이라는
  핵심 제약에도 걸린다 (`docs/problem-statement.md` §2).

## Consequences

### Positive

- 쓰지 않는 동안 비용이 사실상 발생하지 않는다 — 개인 프로젝트에서 가장 중요한 성질이다.
- 태스크 정의·IAM 역할 분리·VPC·ECR·CloudWatch가 코드로 드러나 포트폴리오 표면이 생긴다.
- 온디맨드 태스크가 "복제본 1개" 전제와 일치해 ADR-012를 깨지 않는다.
- 나중에 서비스형으로 바꾸는 것은 같은 태스크 정의에 서비스를 붙이는 일이라 전환이 짧다.

### Negative

- **콜드 스타트가 있다.** 3.46GB 이미지를 매 실행마다 풀한다. 34.86s짜리 작업 앞에 이미지 풀
  시간이 붙으므로 **체감 지연은 로컬보다 나쁠 것이다.** 지연이 중요한 용도가 아니라 수용하지만
  실측하지 않았다.
- Fargate는 인스턴스 단가로 보면 EC2보다 비싸다. 실행량이 크게 늘면 다시 볼 항목이다.
- AWS 종속이 생긴다. 2026년 말 서빙 경로 전환(`CLAUDE.md`)과는 별개 축이지만, 이동성이
  EKS보다 낮은 것은 사실이다 — 다만 태스크 정의는 결국 "이미지 + 환경변수 + 로그 설정"이라
  이식 비용이 크지는 않다.

### Risks

- **`var/`를 클라우드에서 어디에 둘지가 미정이다.** 로컬에서는 named volume이고 기준은
  "로컬 파일시스템 권한 따름"인데(`docs/governance.md`), **클라우드에서는 그 기준이 성립하지
  않는다.** Fargate 태스크의 로컬 스토리지는 태스크 종료와 함께 사라지므로 감사 로그(ADR-007)가
  **사라진다.** EFS나 S3로 빼야 하고, 그 순간 보존 기간·접근 주체를 다시 정해야 한다.
  **세션 7의 선행 결정이다.**
- **무인증 엔드포인트 문제가 클라우드로 따라간다.** `VLLM_BASE`를 SSM SecureString으로 넣어도
  **엔드포인트 자체는 여전히 인증이 없다** (owasp-notes §4). 우리가 소유자가 아니라 IP
  화이트리스트를 걸 수도 없다. 사내 보안 정책 확인은 session-03부터 열려 있는 항목이고
  **배포는 이 질문의 답을 바꾸지 않는다 — 노출 지점만 하나 늘린다.**
- 비용 수치가 list price 추정이다. 리전·데이터 전송·CloudWatch 수집량에 따라 달라진다.
  결정을 뒤집을 크기는 아니지만(고정비 $0 vs $73) apply 전에 갱신해야 한다.
- ECR 이미지가 쌓이면 저장 비용이 선형으로 는다. 수명주기 정책이 필요하다 (Terraform에 포함).

## Reversibility

- **Reversible:** Yes
- **Rollback:** `terraform destroy`. 이번 세션이 만드는 리소스는 ECR 리포지토리와 로그
  그룹뿐이고 둘 다 상태가 없다(이미지·로그는 재생성 가능). 애플리케이션은 AWS를 전제하지
  않는다 — 설정은 환경변수로만 들어가므로(ADR-003, ADR-010) 로컬 compose 경로가 그대로 남는다.
- **Migration Cost:** Low — 배포한 것이 결국 "이미지 + 환경변수 + 로그 설정"이라 다른
  런타임으로 옮겨도 이미지가 그대로 쓰인다.

## Review Trigger

- 이 프로젝트에 실제로 HTTP API가 생기는 경우 — App Runner의 구조적 기각 사유가 사라지므로
  다시 비교한다.
- 여러 워크로드가 한 클러스터를 공유해 고정비가 분산되는 경우, 또는 상시 실행 컴포넌트가
  생겨 고정비가 유휴 비용이 아니게 되는 경우 — EKS를 다시 비교한다.
