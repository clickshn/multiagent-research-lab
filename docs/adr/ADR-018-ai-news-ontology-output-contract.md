# ADR-018: ai-news-ontology 코퍼스를 파일 기반 출력 계약(JSONL)으로 받는다

- **Status:** Proposed
- **Date:** 2026-09-17
- **Decision:** `ai-news-ontology`와 MARA는 코드를 공유하지 않고, 버전이 붙은 JSONL 파일 형식 하나(`docs/contracts/ai-news-ontology-export-v1.md`, `contract_version=1.0`)만 공유한다. 온톨로지 통제어휘는 생산자 쪽 Enum을 정본으로 따르고, 색인·인용 단위는 원문 텍스트로 한정한다.
- **Scope:** multiagent-research-lab (코퍼스 반입 경로 / 레포 간 인터페이스)
- **Decision Source:** Human

---

## Context

### Problem

MARA의 코퍼스는 session-03 이후 arXiv 초록 16건에서 멈춰 있고, ADR-004가 화이트리스트에
열어 둔 `news` 출처는 **한 건도 채워지지 않았다**(ADR-004 Implementation의 유일한 미완
체크박스). 원인은 설계가 아니라 외부 조건이다 — arXiv API가 이 IP를 429로 제한한다.

같은 사람이 운영하는 별도 레포 `ai-news-ontology`는 공개 RSS/Atom 5개 소스에서 AI
뉴스·논문을 수집해 **온톨로지 5필드(기술영역·발표유형·관련기업·관련기존기술·영향도)로
구조화**하고 있다. 코퍼스가 이미 있고, 구조화된 메타데이터까지 붙어 있다. 두 레포를
어떻게 잇느냐가 이번 결정이다.

조사 결과 **Obsidian Vault의 노트를 MARA가 그대로 읽을 수 없다**는 것이 확인됐다.
취향 문제가 아니라 4가지 사실 때문이다.

1. **노트에 원문 본문이 없다.** 본문 섹션에 실리는 텍스트는 `ontology.summary`(한국어
   2~3문장)뿐이고 `RawItem.body`는 프롬프트에만 쓰이고 버려진다
   (`obsidian_writer/mapper.py: render_body()`). 생산자 레포의 골든셋 파일이 직접
   적어 놓았다 — *"수집 파이프라인은 본문을 보존하지 않는다. 이 파일이 원문의 유일한
   사본이다."*
2. **안정적 문서 ID가 없다.** 파일명이 `{처리일}-{소스}-{제목슬러그}.md`이고 슬러그
   충돌 시 `-2`, `-3`이 붙는다. 처리 시각·제목·처리 순서에 의존한다. 동일성 판정은
   frontmatter `source_url` 비교로만 한다.
3. **발행일·수집일이 유실된다.** `RawItem`에는 있지만 frontmatter에는 `date`(=처리일)와
   `processed_at`만 실린다.
4. **Vault는 사람이 손으로 고치는 디렉터리다.** 생산자 코드 자신이 "사용자가 손으로
   고친 노트가 파싱되지 않을 수 있다"는 전제로 YAML 전체 파싱을 피하고 있다.

즉 사람용 종착지(Vault)와 기계용 종착지는 애초에 다른 산출물이어야 한다.

### Constraints

- **출처 제시가 1순위 제약이다**(`docs/problem-statement.md` §3 목표 2). 검색 결과에
  `doc_id`와 `locator`가 항상 함께 실려야 하고, 문서 ID는 재실행해도 같아야 한다.
- **모델 고정 원칙**(ADR-002). 온톨로지 5필드는 외부 벤더 모델(`claude-opus-5`)과 특정
  프롬프트 버전(`extract_ontology.v4.md`)의 출력이다. 이 정보 없이 코퍼스를 받으면
  **하네스 효과를 재려는 전제가 코퍼스 쪽에서 조용히 깨진다.**
- **반입 범위**(ADR-004). 공개 자료만 넣는다. ADR-004는 합성 문서를 *"출처 자체가
  지어낸 것이면 측정에 의미가 없다"*는 이유로 기각했다 — 모델이 쓴 파생 텍스트
  (`summary`, `impact_rationale`)를 인용 근거로 삼으면 이 기각의 취지가 훼손된다.
- **두 레포가 둘 다 arXiv cs.CL을 수집한다.** 같은 논문이 두 출처로 들어가면
  `min_citations` 판정이 부풀고 골든셋 `expected_doc_ids`가 무엇을 가리키는지 알 수
  없어진다.
- **본문 커버리지가 소스마다 크게 다르다.** 뉴스 피드 다수가 본문을 사실상 주지 않는다
  (Evidence 참고).
- 생산자 레포는 MARA의 세션 주기와 무관하게 독립적으로 바뀐다. 어휘가 늘어나거나
  프롬프트 버전이 올라가는 일이 계속 일어난다.

## Decision

### Selected

- **Technology:** 버전이 붙은 JSONL 스냅샷 파일 + manifest (별도 런타임·서비스 없음)
- **Architecture:** 두 레포는 서로를 import하지 않고, 상대가 살아 있어야 동작하지도
  않는다. 공유하는 것은 `contract_version`이 박힌 파일 형식 하나뿐이다. export의 소스는
  Vault가 아니라 파이프라인 중간 산출물(`RawItem` + `NewsOntology` + 실행 메타)이며,
  Vault 쓰기와 export는 같은 입력에서 갈라지는 **형제 출력**이다.
- **Implementation:** 계약 전문은 `docs/contracts/ai-news-ontology-export-v1.md`. 핵심 4가지:
  - **`doc_id`를 결정적으로 생성한다.** URL 정규화(추적 파라미터 제거·쿼리 정렬·프래그먼트
    제거) 후 `news:<sha256(canonical_url)[:16]>`, arXiv 항목은 `arXiv:<id><version>`.
    **arXiv는 MARA의 기존 표기와 바이트 단위로 같게 만들어** 중복을 "탐지할 문제"가
    아니라 "같은 키의 같은 문서"로 만든다.
  - **`provenance`를 필수 필드로 둔다.** `extraction_model` / `prompt_version` /
    `prompt_sha256` / `extracted_at` / `vocab_version` 중 하나라도 없으면 import 실패다.
  - **통제어휘는 생산자가 정본.** MARA는 복제하지 않고 manifest의 어휘 스냅샷과 대조만
    한다. 값 **추가**는 통과, **삭제·이름 변경·쪼개짐**은 import 실패 — 이미 인덱싱된
    문서의 라벨이 소급해서 틀려지기 때문이다.
  - **원문 텍스트만 색인한다.** `indexable = (text_origin=="source_text") and
    (text_chars >= MIN_TEXT_CHARS)`. `summary`·`impact_rationale`은 메타데이터로만 싣고
    색인·인용 경로에 넣지 않는다. `MIN_TEXT_CHARS`는 v1에서 1(비어 있지 않음)이고,
    실제 값은 `text_chars` 분포를 본 뒤 측정으로 정한다.
  - **`text` 길이 상한 4,000자를 계약 상수로 고정한다.** 생산자의 `BODY_MAX_CHARS`를
    참조하지 않고 복사해 박는다. 목적은 생산자의 열린 항목 D-013(원문 페이지 fetch)이
    나중에 실행돼도 **계약 형식이 그대로 유지되게** 하는 것이다. 다만 상한이 흡수하는
    것은 형식이고, **"기사 전문을 반입해도 되는가"는 ADR-004 재검토 사안으로 남는다.**
  - 온톨로지 5필드 중 **검색 필터 후보는 `release_type` 하나**이고, 나머지는 메타데이터로만
    싣는다 (Alternatives 참고). **배선 자체는 이 결정의 범위가 아니다** — Session 0.5는
    메타데이터 적재까지이고, 필터 배선은 Session 3에서 **그것 하나만 바꿔** 대조한다.
    코퍼스 구성과 검색 조건이 한 번에 바뀌면 수치가 움직인 원인을 가를 수 없다.

## Rationale

1. **파일은 버전을 붙일 수 있고 커밋할 수 있다.** MARA의 재현 기준은 인덱스가 아니라
   스냅샷이다(ADR-004). 계약을 파일로 두면 "어떤 코퍼스로 잰 수치인가"가 커밋 하나로
   답해진다. 런타임 결합이었다면 같은 질문에 답할 수 없다.
2. **결합을 끊는 것이 이 프로젝트의 목적에 부합한다.** MARA가 검증하려는 것은 하네스가
   결과 품질을 얼마나 좌우하는가다. 생산자 레포의 가용성·스키마 변경이 MARA 실행에
   직접 영향을 주면, 측정 대상이 아닌 변수가 하나 늘어난다.
3. **`provenance` 필수화가 ADR-002를 코퍼스 쪽까지 연장한다.** 모델을 고정해 놓고
   코퍼스가 외부 모델 버전의 함수로 흔들리면 고정의 의미가 없다. 프롬프트 해시까지
   싣는 이유는 생산자 레포가 이미 같은 이유로 그렇게 하고 있기 때문이다(그쪽 D-041).
4. **파생 텍스트를 인용 경로에서 빼는 것이 ADR-004의 연장선이다.** `summary`는 지어낸
   것은 아니지만 모델의 패러프레이즈다. 그것을 인용하면 인용이 원문이 아니라 모델
   출력을 가리킨다. 인용 정확도가 1순위 지표인 시스템에서 이 구분을 흐리면 지표 자체가
   무의미해진다.
5. **어휘를 복제하지 않는 것이 드리프트를 구조적으로 막는다.** 복제하면 두 곳이 갈리고,
   갈린 것을 알아챌 방법이 없다. `ALLOWED_SOURCES`와 성격이 다르다 — 저쪽은 *우리가
   지켜야 할 정책*이라 코드에 박고, 이쪽은 *남의 레포가 정하는 사실*이라 받아서 대조한다.
6. **한국어 소스가 코퍼스에 들어온다.** 현재 골든셋 9건이 전부 한국어 질의인데 코퍼스는
   전부 영어라, 크로스링구얼이 변수가 아니라 **상수**다(session-08 §7, ADR-005
   Amendment). GeekNews 유입은 이 상수를 변수로 바꾸는 유일한 현실적 경로다.

## Evidence

- **Production Data:** 생산자 레포 실측(소스당 최근 50건 표본, 본문 길이 중앙값,
  그쪽 결정 로그 D-013/D-014) — arXiv cs.CL **1,339자** / GeekNews **160자**(0자 항목
  없음, 40/50건이 말줄임 절단) / OpenAI News **149자** / Google DeepMind Blog **97자**
  (15/50건이 0자) / Hugging Face Blog **0자**(50/50건). **뉴스 피드 다수가 본문을 주지
  않는다**는 것이 "원문만 색인" 정책의 커버리지 비용을 결정한다.
- **Production Data:** 통제어휘 규모 — 기술영역 14, 발표유형 8(`extraction/schema.py`).
  생산자 확정 골든셋 3건에서 **발표유형 8개 중 3개만 실사용**됐다.
- **Production Data:** MARA 현 코퍼스 16건(arXiv 2개 주제), 골든셋 9건 중 근거 있는
  케이스 7건 — 전부 한국어 질의, 코퍼스는 전부 영어.
- **Cost:** 생산자 레포 실측 기준 게이트+추출 비용은 100건당 약 **$2.92**(게이트 도입 전
  $4.29, 약 32% 절감). 초기 코퍼스 목표 규모(250건 ≈ **$7**)를 이 값으로 역산했고,
  **1단계 30건 ≈ $0.9 / 2단계 220건 ≈ $6.4**로 쪼갰다 (Implementation).

## Alternatives

### 레포 통합 (모노레포)

- **Pros:** 스키마를 공유하므로 계약 문서·버전·검증 코드가 통째로 필요 없다. 어휘 드리프트가 구조적으로 불가능해진다. 한 번의 변경으로 양쪽이 같이 움직인다.
- **Cons:** 두 레포의 제약이 정반대다. 생산자는 **외부 벤더 모델(`claude-opus-5` / Anthropic API)을 전제로 설계돼 있고**, MARA는 **외부 LLM 벤더 비의존**과 자체 서빙 엔드포인트를 전제로 설계돼 있다(ADR-003). 합치면 한 레포 안에 상반된 두 전제가 공존하고, 어느 쪽 제약이 어디까지 적용되는지 경계가 사라진다. 또한 MARA는 이미 공개 레포로 v1.0 태그가 붙어 있고 배포(ECS/Fargate·EFS) 경계가 그 단위로 잡혀 있다(ADR-013·ADR-015) — 통합은 인프라 경계까지 다시 그리는 일이 된다. 두 레포의 테스트·의존성·Python 버전 제약도 각각이다(MARA는 Python 3.14 + Pydantic V1 경고 문제를 안고 있다).
- **Rejected because:** 얻는 것(스키마 공유)보다 잃는 것(제약 경계의 소멸)이 크다. **"이 데이터가 외부 벤더로 나가도 되는가"는 이 프로젝트에서 가장 비싼 질문이고**(ADR-004, 사내 보안 정책 미결 상태), 그 경계가 레포 경계와 일치할 때 판단이 단순해진다. 합치는 순간 그 질문에 파일 단위로 답해야 한다.

### 런타임 API 결합 (생산자가 HTTP 엔드포인트로 코퍼스를 서빙)

- **Pros:** 최신 데이터를 항상 받는다. export·import라는 중간 단계가 없어 파이프라인이 짧다. 증분 갱신이 자연스럽다.
- **Cons:** **재현성이 깨진다.** MARA의 측정치는 "어떤 코퍼스 스냅샷에서 나온 수치인가"로 정의되는데(ADR-004), 매 호출마다 응답이 달라지면 같은 인덱스 스냅샷이라는 개념 자체가 성립하지 않는다. 생산자 레포의 가용성이 MARA 실행의 전제가 되고, 두 레포가 **동시에 살아 있어야 하는** 운영 부담이 생긴다(클라우드 배포 시 네트워크 경로·보안그룹까지 따라온다). 무인증 엔드포인트를 하나 더 만드는 것은 이 프로젝트가 이미 겪고 있는 문제(ADR-003·governance "시크릿 취급")를 자발적으로 늘리는 일이다.
- **Rejected because:** 실시간성은 이 프로젝트가 필요로 하는 속성이 아니다. **코퍼스는 하네스를 돌리기 위한 입력이지 검증 대상이 아니고**(ADR-004 Constraints), 검증 대상이 아닌 것 때문에 1순위 요구(재현성)를 내주는 교환이다.

### Obsidian Vault를 MARA가 직접 파싱

- **Pros:** 생산자 쪽에 새 코드를 한 줄도 넣지 않아도 된다. 이미 노트가 쌓이고 있다.
- **Cons:** Context에 적은 4가지 — 본문 부재, 안정적 ID 부재, 발행일 유실, 사람이 손으로 고치는 디렉터리. 특히 **본문이 없다**는 것은 보완이 아니라 차단이다. 노트에 있는 텍스트는 모델이 쓴 한국어 요약뿐이라, 그것을 색인하면 인용이 원문이 아니라 패러프레이즈를 가리킨다.
- **Rejected because:** 인용 단위가 될 원문 텍스트를 Vault에서 얻을 수 없다. 나머지 3가지를 전부 해결하더라도 이 하나가 남는다.

### 온톨로지 5필드를 전부 검색 필터로 배선

- **Pros:** 구조화의 이득을 최대한 쓴다. "RAG 관련 오픈소스 발표"류 질의를 필터 조합으로 정확히 좁힐 수 있다.
- **Cons:** 필드마다 성질이 다르다. `tech_domains`는 MARA 골든셋 9건이 전부 멀티에이전트/LLM 에이전트 주제라 `Agent`/`Eval`로 수렴해 **100건 규모에서 선택도가 없다**. `companies`는 정밀도가 높지만 **현 골든셋에 기업명이 하나도 없어 수요가 0**이다. `prior_art`는 사전이 없는 열린 어휘라 **열거할 수 없는 값으로는 필터를 만들 수 없다**. `impact_score`로 거르는 것은 **모델의 주관 점수로 근거를 버리는 것**이라, 인용 정확도가 1순위인 시스템에서 위험한 방향이다.
- **Rejected because:** 근거 없이 정한 손잡이를 또 늘리게 된다. MARA에는 이미 `min_citations`·`top_k`가 근거 없는 출발점으로 남아 있다(session-08 §7). 값 분포가 **미측정**인 상태에서 5개를 한꺼번에 배선하면 어느 필터가 무엇을 했는지 영원히 분리할 수 없다.
- **Recheck if:** 첫 export의 manifest `counts.by_release_type` / `by_tech_domain` 분포가 위 예측을 뒤집는 경우, 또는 골든셋에 기업명·기술 태그를 지목하는 질의가 추가되어 실제 수요가 생기는 경우.

### 요약(`summary`)을 색인 대상에 포함

- **Pros:** 본문이 비어 있는 소스(Hugging Face Blog 50/50건, DeepMind 15/50건)도 코퍼스에 들어와 초기 규모가 커진다. 한국어 텍스트가 대량 확보되어 크로스링구얼 대조군을 바로 만들 수 있다.
- **Cons:** 인용의 일부가 원문이 아니라 **모델 패러프레이즈**를 가리키게 된다. 어느 인용이 원문이고 어느 것이 파생인지 매번 구분해서 집계해야 하고, 그 구분을 한 번이라도 놓치면 근거 정확도 수치가 조용히 오염된다.
- **Rejected because:** ADR-004가 합성 코퍼스를 기각한 이유("출처 자체가 지어낸 것이면 측정에 의미가 없다")와 같은 논리다. 파생 텍스트는 지어낸 것은 아니지만, 인용 정확도가 1순위 지표인 시스템에서 **인용 대상이 모델 출력인 경우를 허용하면 지표의 의미가 흐려진다.** 계약에 `text_origin` 필드를 지금 만들어 두되 v1에서는 `source_text` 한 값만 유효하게 해서, 나중에 뒤집더라도 스키마 변경이 아니라 값 추가로 끝나게 한다.

## Consequences

### Positive

- ADR-004가 열어 두고 채우지 못한 `news` 출처가 채워진다. 범위 확대가 아니라 **이미 승인된 범위의 미집행분 집행**이다.
- **한국어 문서가 코퍼스에 들어온다.** "한국어 질의 + 영어 코퍼스"라는 상수 조건이 깨지고, 크로스링구얼이 비로소 측정 가능한 변수가 된다(session-08 §7 (다)).
- arXiv 항목이 `doc_id` 규칙으로 기존 스냅샷과 같은 키를 갖게 되어, 429로 막힌 코퍼스가 다른 경로로 늘어날 수 있다. 중복은 병합으로 흡수된다.
- `provenance`가 필수라서 코퍼스 드리프트(모델·프롬프트 버전 변경)를 **탐지할 수 있다.** 지금까지 MARA가 탐지 수단을 갖지 못한 종류의 변화다(엔드포인트 모델 지문 문제와 같은 계열).
- 두 레포가 각자의 제약(외부 벤더 의존 여부)을 레포 경계에서 유지한다.

### Negative

- export/import라는 단계가 하나 늘고, 계약 문서·검증 코드·버전 관리라는 유지비가 생긴다. 모노레포였다면 없을 비용이다.
- 실시간성이 없다. 생산자 쪽 새 기사가 MARA 코퍼스에 들어오려면 export를 돌리고 커밋해야 한다.
- **본문이 없는 소스가 통째로 빠진다.** Hugging Face Blog는 50/50건이 본문 0자라 색인 대상이 하나도 없고, DeepMind도 부분적으로 빠진다. 소스 다양성이 계획보다 좁아진다.
- 온톨로지 5필드 중 4개가 메타데이터로만 실린다 — 당장은 저장 비용만 발생하고 검색에 기여하지 않는다.

### Risks

- **생산자 쪽 어휘가 쪼개지면 import가 실패한다.** 이것은 설계된 동작이지만, 실제로 발생하면 재인덱싱 전까지 코퍼스 갱신이 멈춘다.
- **`doc_id` 규칙이 바뀌면 과거 측정값이 전부 무효가 된다.** URL 정규화 규칙이 계약에서 가장 되돌리기 비싼 부분이다.
- 값 분포가 **미측정**이라, `release_type`을 필터로 고른 판단 자체가 첫 export에서 뒤집힐 수 있다.
- 생산자 레포에서 본문 fetch(그쪽 열린 항목 D-013)가 구현되면 피드 발췌가 아니라 **기사 전문**이 반입된다. **계약 형식은 이 변화를 흡수한다** — 4,000자 상한이 계약 상수로 박혀 있어 `contract_version`을 올릴 일이 없다. **흡수되지 않는 것은 판단 쪽이다:** 저작권과 반입 범위는 **ADR-004 재검토 사안**으로 그대로 남는다. 계약이 준비돼 있다는 것과 반입해도 된다는 것을 같은 말로 읽지 않아야 한다.
- 필드 소비 등급이 **미측정 예측**이라, Session 0.5의 manifest 분포가 예측을 뒤집으면 Session 3의 필터 대상 자체가 바뀐다. 계약 §8.1에 판정 임계값을 **데이터를 보기 전에** 적어 둔 이유다 — 분포를 본 뒤 기준을 정하면 어떤 결과에도 해석을 붙일 수 있다.
- 코퍼스 생산에 외부 벤더 API 비용이 든다(100건당 약 $2.92). MARA의 무료 할당 자원 밖이므로 **governance의 승인 게이트 대상**이고, Implementation에서 **1단계 $0.9 / 2단계 $6.4**로 쪼갰다. 쪼갠 이유는 금액 자체가 아니라 **실패 시 손실의 크기**다 — 형식 결함은 표본 수에 비례해 드러나지 않으므로 30건에서 걸러낼 수 있는 것을 250건 쓰고 발견하면 같은 돈을 다시 낸다.

## Implementation

**Session 0.5 — 계약이 흐르는 것까지. 검색 경로는 건드리지 않는다.**

외부 벤더 API 호출은 **2단계 승인 게이트**로 나눈다. 스키마·형식 결함은 표본 수에
비례해 드러나지 않으므로, **250건을 다 쓴 뒤 결함을 찾으면 비용을 두 번 낸다.**

*1단계 — 계약 e2e 검증 전용, 30건 ≈ $0.9*

- [ ] 생산자 쪽 export 스크립트 — `RawItem` + `NewsOntology` + 실행 메타 → JSONL + manifest
- [ ] export 스크립트에 **`--urls` 입력** 추가 — 중복 케이스를 명시적으로 넣기 위해 필요하다. 생산자는 arXiv *최근* 피드를, MARA는 *주제 질의 결과*를 갖고 있어 **겹칠 이유가 구조적으로 없다.** 없으면 `doc_id` 동일화가 검증되지 않은 채 통과한 것처럼 보인다
- [ ] `doc_id` 생성 규칙(URL 정규화 + arXiv 특례)을 양쪽에서 **같은 규칙으로** 구현하고 동일 입력·동일 출력 테스트
- [ ] MARA `src/tools/corpus.py` — `.jsonl` 로더, 온톨로지 메타데이터 적재(`CorpusDoc.as_metadata()`가 현재 스칼라 6키만 싣고 `extra`를 버린다), 계약 §7 검증 7종
- [ ] 계약 위반 케이스 테스트(어휘 이탈·`doc_id` 중복·`provenance` 누락·`indexable` 불일치·`text` 상한 초과)
- [ ] **표본 30건으로 계약 §12.2 체크리스트 13항목 판정** — 중복 케이스 2건(`arXiv:2412.05449v1`, `arXiv:2605.21404v1`) 포함
- [ ] 1단계 추출 결과 원본을 로컬 보존 — 형식 결함 수정 시 **LLM 재호출 없이 재-export** (계약 §12.3)

*2단계 — 코퍼스 확보, 220건 ≈ $6.4. **§12.2 전 항목 통과 후에만 실행한다***

- [ ] 나머지 수집·추출·export, `news` 출처 색인 가능 100건 확보
- [ ] manifest 분포로 계약 §8.1의 필드 소비 등급 **예측을 검증** (사전 등록한 임계값으로 판정)
- [ ] `docs/eval/golden-set.json`의 `corpus` 블록 갱신 — 코퍼스가 늘어나면 `expected_doc_ids`를 다시 확인해야 한다(골든셋 파일 자신의 주의사항)

**Session 3 — 여기서만 검색 조건을 바꾼다 (이 ADR의 범위 밖, 경계를 명시하기 위해 적는다).**

- [ ] MARA `src/tools/retrieval.py` — `release_type` 필터를 기존 `where` 경로에 배선하고, **그것 하나만** 바꿔 대조 측정

> **0.5에서 필터까지 배선하지 않는 이유:** 코퍼스가 10배가 되는 변경과 검색 조건이 바뀌는
> 변경을 같은 세션에 넣으면, 수치가 움직였을 때 **어느 쪽 때문인지 영원히 가를 수 없다.**
> 모델을 고정하고 하네스만 움직이는 원칙(ADR-002)이 여기에도 그대로 적용된다.

## Reversibility

- **Reversible:** Partial
- **Rollback:** 코퍼스에서 빼는 것은 `data/corpus/news/*.jsonl` 삭제 + `build_index.py --reset`이라 비용이 낮다. 되돌리기 비싼 것은 **`doc_id` 규칙**이다 — 골든셋 `expected_doc_ids`와 과거 실행의 인용 표기에 박혀 있어, 규칙을 바꾸면 재인덱싱뿐 아니라 골든셋 기대값과 그 위에서 잰 모든 수치를 다시 만들어야 한다. 그래서 규칙 변경은 `contract_version` major 인상 사안이다.
- **Migration Cost:** Low (코퍼스 제거) / High (`doc_id` 규칙 변경)

## Review Trigger

- 첫 export의 manifest `counts.by_release_type` / `by_tech_domain` 분포가 필드 소비 등급 예측(`release_type`만 필터로 유용하다)을 뒤집는 경우 — 필드 배선 재검토.
- 골든셋에 기업명·기술 태그를 지목하는 질의가 추가되어 `companies` / `tech_domains` 필터에 실제 수요가 생기는 경우 — 해당 필드 배선 재검토.
