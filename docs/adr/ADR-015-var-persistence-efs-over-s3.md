# ADR-015: 클라우드에서 `var/`(traces·llm_cache·chroma)는 EFS에 둔다

- **Status:** Proposed
- **Date:** 2026-09-16
- **Decision:** ECS Fargate 태스크에 **Amazon EFS**를 마운트해 `var/traces`·`var/llm_cache`·`var/chroma`를 영속화한다. S3는 기각한다. 판단 기준은 **기존 코드를 고치지 않고 올릴 수 있는가**다.
- **Scope:** multiagent-research-lab (배포 / 영속 저장소 / 세션 7)
- **Decision Source:** Human

---

## Context

### Problem

ADR-013이 배포 대상을 Fargate 온디맨드 태스크로 정하면서 **의도적으로 태스크 정의를 쓰지
않고 남겨 뒀다.** 이유가 이것이다 — Fargate 태스크의 로컬 스토리지는 **태스크 종료와 함께
사라진다.** 저장소를 정하지 않고 태스크 정의를 쓰면 **감사 로그(ADR-007)가 매 실행마다
증발하는 구성**을 코드로 굳히게 된다. 감사 로그 요구는 규제성이라 나중에 붙이기 어렵고,
State에 `trace`를 미리 넣어 둔 이유가 그것이다.

세션 6 핸드오프가 이 항목을 "세션 7 apply의 가장 중요한 선행 결정"으로 남겼다.

영속화 대상은 세 가지이고 성격이 다르다.

| 디렉터리 | 내용 | 접근 패턴 | 사라지면 |
| --- | --- | --- | --- |
| `var/traces` | 프롬프트·응답을 담은 감사 로그 JSONL (ADR-007) | **append** | 감사 요구 미충족 |
| `var/llm_cache` | LLM 응답 본문 캐시 (ADR-008) | 키로 읽기/쓰기 | 재현 실행이 매번 과금·지연 |
| `var/chroma` | 벡터 인덱스 (SQLite + 파일, ADR-005) | **랜덤 읽기/쓰기, 파일 락** | 매 실행 10.5s 재색인 |

### Constraints

- **기존 코드가 POSIX 파일시스템 호출로 읽고 쓴다.** `Tracer`는 JSONL에 append하고, 캐시는
  파일 경로로 조회하며, Chroma 임베디드는 로컬 디렉터리를 SQLite로 연다.
- **컨테이너는 non-root(uid 10001)로 돈다** (ADR-010 Dockerfile). 쓰기 권한이 맞아야 한다.
- **유휴 고정비가 0에 수렴해야 한다** (ADR-013). 저장소가 그 전제를 깨면 안 된다.
- **`var/`의 보존 기간·접근 주체 기준은 로컬 전용이었다** (`docs/governance.md`, 세션 6).
  클라우드로 옮기는 순간 "로컬 파일시스템 권한"이라는 근거가 사라지므로 **이 결정과 함께
  다시 정해야 한다.**
- 복제본은 1개다 (ADR-012의 Chroma 임베디드 전제). 동시 쓰기를 가정하지 않는다.

## Decision

### Selected

- **Technology:** Amazon EFS (Standard, `throughput_mode = bursting`, 저장 시 암호화).
- **Architecture:** 파일시스템 **1개** + AZ별 마운트 타깃 2개 + **액세스 포인트 3개**
  (`/traces`, `/llm_cache`, `/chroma`). 액세스 포인트가 docker-compose의 named volume
  3개와 1:1로 대응하고, 각각 자기 디렉터리에 chroot되어 서로를 보지 못한다.
- **Implementation:**
  - 액세스 포인트의 `posix_user`가 uid/gid를 **10001로 강제**한다 → non-root 컨테이너가
    그대로 쓴다. 로컬 compose에서 볼륨 소유권을 맞춰 준 것과 같은 상태가 된다.
  - 태스크 정의의 `transit_encryption = ENABLED` + `authorization_config.iam = ENABLED`.
  - 파일시스템 정책이 **태스크 역할만** 허용하고, 비TLS 접근을 명시적으로 거부한다.
  - 태스크 역할 정책은 `elasticfilesystem:AccessPointArn` 조건으로 **액세스 포인트 경유만**
    허용한다. 루트 마운트를 막지 않으면 액세스 포인트 격리가 무의미해진다.
  - `ClientRootAccess`는 **주지 않는다** — 주면 uid 0으로 쓸 수 있어 `posix_user` 강제가 풀린다.
  - 파일: `infra/terraform/efs.tf`, `iam.tf`, `ecs.tf`.

## Rationale

1. **재작성이 없다.** EFS는 NFS로 마운트되므로 POSIX 시맨틱(append, seek, 파일 락)이 그대로
   동작한다. `Tracer`·캐시·Chroma 세 모듈 중 **한 줄도 고치지 않는다.** 이번 배포의 목적은
   "돌아가는 것을 올리는 것"이지 "올리려고 고쳐 쓰는 것"이 아니다.
2. **검증된 스택과 배포된 스택이 같아진다.** 세션 6이 컨테이너 안에서 114건 통과·e2e 13콜을
   실측했다. 저장 계층을 바꾸면 그 실측이 배포본에 대한 근거가 되지 못한다. ADR-013이
   App Runner를 기각한 논리("올리려면 안 쓸 웹 API를 감싸야 하고, 그러면 배포한 것이 검증한
   스택과 달라진다")와 같은 기준이다.
3. **액세스 포인트가 접근 통제의 단위가 되어 준다.** governance가 요구하는 "접근 주체"를
   IAM 역할 + 액세스 포인트로 **기계가 집행하는 형태**로 쓸 수 있다. 로컬에서는 "그 머신에
   로그인할 수 있는 주체"라는 서술뿐이었다.
4. **유휴 고정비를 깨지 않는다.** 최소 요금이 없고 쓴 GB만 과금된다. 마운트 타깃·액세스
   포인트는 무료다. `bursting` 모드는 처리량 요금이 없다.

## Evidence

- **Cost:** EFS Standard $0.33/GB-월 (ap-northeast-2, list price). 현재 데이터는 트레이스
  JSONL 33개 + 캐시 92개 + 16건 코퍼스 인덱스로 **100MB 미만** → 월 **$0.04 미만**.
  30일 미접근 시 IA($0.016/GB-월)로 내려간다. 마운트 타깃 2개·액세스 포인트 3개 = $0.
- **Experiment:** `terraform validate` 통과 (Terraform v1.16.2, hashicorp/aws v5.100.0).
  **세션 7에서 CLI를 설치하고 처음으로 돌렸다** — 세션 6의 HCL은 미검증 상태였다.
  ⚠️ `validate`는 문법·스키마 검사다. **`plan`/`apply`는 자격증명이 없어 아직 돌리지 못했다.**

## Alternatives

### S3 (객체 스토리지)

- **Pros:** 저장 단가가 EFS의 1/14이다($0.023/GB-월). 유휴 비용이 더 낮고, 수명주기 정책과
  버전 관리·객체 잠금 같은 감사 친화적 기능이 풍부하다. 마운트 타깃이 없어 VPC 구성도 단순하다.
- **Cons:** **객체 스토리지라 append도 seek도 없다.** 세 모듈을 전부 고쳐야 한다 —
  `Tracer`는 트레이스 단위로 객체를 쓰도록, 캐시는 S3 클라이언트를 쓰도록, Chroma는
  SQLite 파일을 열 수 없으니 **매 실행 전 다운로드 → 종료 시 업로드**하는 절차를 붙이거나
  서버형으로 바꿔야 한다(= ADR-012를 뒤집는다).
- **Rejected because:** **배포 때문에 검증된 코드를 바꾸게 된다.** 저장 단가 차이는 월
  $0.04 대 $0.003으로 **연 $0.5 미만**이다 — 세 모듈 재작성과 재검증의 대가로 얻는 것이
  그 금액이다. 그리고 Chroma를 "다운로드-업로드"로 감싸는 순간 태스크가 중간에 죽으면
  인덱스가 깨지는 새 실패 모드가 생긴다.

### S3 + FUSE 마운트 (Mountpoint for Amazon S3)

- **Pros:** S3 단가를 쓰면서 파일시스템처럼 보인다.
- **Cons:** **append와 랜덤 쓰기를 지원하지 않는다.** 순차 쓰기 전용이라 JSONL append와
  SQLite 양쪽 다 못 쓴다. 즉 "고치지 않아도 된다"는 EFS의 장점을 얻지 못한다.
- **Rejected because:** S3의 제약을 그대로 물려받아 재작성을 피하지 못한다. 이름만 파일시스템이다.

## Consequences

### Positive

- 코드 변경 0. 세션 6의 컨테이너 실측이 배포본에 대한 근거로 그대로 유효하다.
- 감사 로그가 태스크 종료 후에도 남는다 — ADR-007 요구가 클라우드에서도 충족된다.
- 재색인 10.5s가 매 실행에서 사라진다 (인덱스가 EFS에 남는다).
- 접근 통제가 서술이 아니라 IAM 정책·액세스 포인트로 집행된다.

### Negative

- VPC·마운트 타깃·보안그룹이 필요해져 리소스 개수가 늘었다 (2개 → 14개 종류).
  ADR-013의 "최소 구성" 기조에서 멀어진다.
- EFS는 S3보다 14배 비싸다. 지금은 절대액이 작아 무의미하지만 **데이터가 GB 단위로
  커지면 이 비율이 드러난다.**
- NFS 지연이 로컬 디스크보다 크다. Chroma 질의 지연에 영향을 줄 수 있고 **측정되지 않았다.**

### Risks

- ⚠️ **이 결정은 `var/` 보존·접근 기준을 무효화한다.** 세션 6이 확정한 기준("로컬 파일시스템
  권한 따름")의 근거가 사라진다. `docs/governance.md`를 EFS 기준으로 다시 썼다 — 이 ADR과
  **한 몸으로 읽어야 한다.**
- ⚠️ **ADR-004 전제 의존은 그대로다.** "공개 arXiv 초록만 넣는다"가 깨지면 EFS 암호화
  키(AWS 관리 키)·보존 기간·접근 주체를 다시 정해야 한다. 클라우드로 옮겼다고 이 조건이
  해소된 것이 아니다 — **노출 경로가 로컬 디스크에서 AWS 계정으로 바뀌었을 뿐이다.**
- ⚠️ **복제본이 2개 이상이 되면 Chroma 임베디드 전제가 깨진다** (ADR-012). EFS는 동시
  마운트를 허용하므로 **저장소가 막아 주지 않는다.** 오히려 "여러 태스크가 같은 인덱스를
  쓸 수 있다"는 착각을 만들기 쉽다. SQLite 파일 락이 NFS에서 신뢰할 수 없다는 점도 같다.
- 🔴 **[session-15 갱신] 위 항목은 가설이 아니라 실측이다 — 그리고 예상보다 나쁘다.**
  **질의가 인덱스 파일을 수정한다** (ADR-005 Amendment 4 ②). 읽기 전용 프로세스를 돌린
  전후로 `data_level0.bin`·`length.bin`의 sha256이 바뀌며, **결함 없는 인덱스에서도
  그렇다.** 즉 태스크 2개가 같은 인덱스를 붙들면 **읽기-읽기 경합이 아니라 쓰기-쓰기
  경합이다.** SQLite 락 문제와 별개이고, 액세스 포인트·IAM은 이것을 막지 않는다
  (둘 다 같은 태스크 역할로 정당하게 마운트한다).
  - 더 나쁜 것은 **경합이 조용하다**는 점이다. 같은 경로(벡터 세그먼트 로드/재생)에서
    이미 **프로세스당 문서 1건 유실**이 관측됐고, 그 유실은 `count()`에도 로그에도
    나타나지 않는다.
  - 🔒 **해결될 때까지의 제약: 같은 인덱스에 대한 동시 실행을 금지한다.**
    **`desired_count`를 2 이상으로 올리지 않는다** — 올리기 전에 이 항목을 규명한다.
    병렬이 필요하면 인덱스를 복사해 각자 다른 `CHROMA_DIR`을 쓴다.
  - **인덱스를 읽기 전용 마운트로 두는 회피책은 성립하지 않을 수 있다** — 질의가 쓰기를
    하므로 아예 실패할 수 있다. 미확인.
- EFS bursting 모드는 저장 용량에 비례해 기준 처리량이 정해진다. 데이터가 100MB 수준이면
  기준 처리량이 매우 낮고 **버스트 크레딧에 의존한다.** 지금 규모에서는 문제되지 않지만
  대량 재색인 같은 작업에서 드러날 수 있다 — 측정되지 않았다.

## Implementation

- [x] `infra/terraform/efs.tf` — 파일시스템 / 마운트 타깃 2 / 액세스 포인트 3 / 파일시스템 정책
- [x] `infra/terraform/iam.tf` — 태스크 역할에 액세스 포인트 경유 마운트·쓰기만 부여
- [x] `infra/terraform/ecs.tf` — 태스크 정의에 EFS 볼륨 3개 + 마운트 포인트 3개
- [x] `docs/governance.md`의 `var/` 정책을 EFS 기준으로 재작성
- [x] `terraform validate` 통과
- [ ] `terraform plan` / `apply` — **AWS 자격증명 미구성으로 미실행**
- [ ] 마운트 후 실제 쓰기 확인 (non-root uid 10001이 세 디렉터리에 쓰는지)
- [ ] NFS 지연이 Chroma 질의 지연에 주는 영향 실측

## Reversibility

- **Reversible:** Yes
- **Rollback:** 태스크 정의에서 볼륨·마운트 포인트를 빼면 태스크는 로컬 스토리지로 돌아간다
  (데이터는 휘발). EFS 자체는 `terraform destroy`로 지운다 — **데이터가 함께 사라지므로
  필요하면 먼저 내려받는다.** 저장소를 S3로 바꾸는 경우는 롤백이 아니라 재작성이다.
- **Migration Cost:** Low (EFS 도입 자체), High (나중에 S3로 전환하는 경우 — 세 모듈 재작성)

## Review Trigger

- 오케스트레이터 복제본이 2개 이상이 되어야 하는 경우 — Chroma 임베디드 전제(ADR-012)와
  함께 이 결정도 다시 본다. EFS는 동시 마운트를 막지 않으므로 저장소 쪽에서 경고가 오지 않는다.
- `var/`에 들어가는 데이터가 공개 arXiv 초록을 벗어나는 경우 (ADR-004 전제 붕괴) —
  암호화 키·보존 기간·접근 주체를 이 ADR과 governance에서 함께 재결정한다.
