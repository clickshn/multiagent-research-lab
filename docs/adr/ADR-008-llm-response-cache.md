# ADR-008: LLM 응답 캐시는 프로바이더 계층 데코레이터로 두고 기본은 끈다

- **Status:** Proposed
- **Date:** 2026-09-15
- **Decision:** 동일 입력에 대한 LLM 응답을 디스크에 캐시하는 `CachingLLMProvider`를 `LLMProvider` 데코레이터로 추가한다. 캐시는 **기본 꺼짐**이며 `LLM_CACHE` 환경변수나 `get_provider(cache=True)`로 명시적으로 켠다.
- **Scope:** multiagent-research-lab (프로바이더 계층)
- **Decision Source:** Human

---

## Context

### Problem

session-04에서 비용·지연을 실측하면서 두 가지가 드러났다.

**첫째, 같은 실행 안에서 동일한 프롬프트가 반복된다.** 캐시를 비운 상태로 골든셋
9건을 돌렸는데도 실행 도중 **17건이 캐시에 적중**했다. 재검색 루프가 같은 항목에
같은 검색어를 던져 같은 후보를 받고, 결국 **글자 단위로 동일한 프롬프트**를 다시
보내기 때문이다. 이것은 캐시가 없으면 그냥 중복 청구된다.

**둘째, 재현 실행의 비용이 크다.** 골든셋 재측정·데모·문서 작성은 같은 질의를
여러 번 돌린다. 9건 1회가 LLM 지연 합 141.9초, 토큰 99,856개다. 하네스를 바꾸지
않은 재실행에까지 같은 비용을 낼 이유가 없다.

동시에 **캐시는 측정을 망칠 수 있다.** 이 프로젝트가 재려는 것은 정확히 하네스의
효과인데(ADR-002 모델 고정 원칙), 캐시가 기본으로 켜져 있으면 "이 하네스 변경이
지연을 줄였다"와 "두 번째 실행이라 캐시를 탔다"를 구분할 수 없다.

### Constraints

- 노드 코드는 캐시를 몰라야 한다. 캐시 정책이 네 노드에 흩어지면 하네스 비교
  실험에서 무엇이 바뀐 건지 알 수 없게 된다.
- 프로세스 1건 = 질의 1건인 현재 실행 방식에서 인메모리 캐시는 프로세스와 함께
  사라져 재실행에 도움이 안 된다.
- 감사 로그(ADR-007)는 캐시 적중 호출도 기록해야 한다. "이 답이 어디서 왔는가"에
  "캐시"도 유효한 답이어야 감사가 성립한다.
- 새 유료 리소스를 만들지 않는다 (`docs/governance.md` 승인 게이트).

## Decision

### Selected

- **Technology:** 표준 라이브러리만 사용한다 (`hashlib` + `json` + 파일 시스템).
  새 의존성 없음.
- **Architecture:** `CachingLLMProvider`가 `LLMProvider` 프로토콜을 그대로 구현하며
  내부 프로바이더를 감싼다. 캐시 온/오프가 노드 코드 변경 없이 **설정 하나**로 바뀐다.
- **Implementation:** `src/providers/cache.py`. 캐시 키는 (모델, 메시지, temperature,
  max_tokens, stop)의 SHA-256. 저장 위치는 `var/llm_cache/<앞2글자>/<해시>.json`
  (커밋하지 않는다). `LLMResponse`에 `cached` / `origin_latency_s` 필드와
  `billed_tokens` 속성을 추가해, 계측이 "요청이 요구한 토큰"과 "실제로 청구된 토큰"을
  구분해 세게 한다.

## Rationale

1. **데코레이터라야 변인을 하나만 움직일 수 있다.** 같은 파이프라인·같은 프롬프트를
   캐시만 켜고 끄며 돌릴 수 있어야 캐시의 효과가 분리된다. `bench_golden.py`가
   `--cache` 플래그 하나로 두 조건을 만드는 것이 그 결과다.
2. **디스크여야 세션을 넘는다.** 인메모리 캐시는 프로세스 종료와 함께 사라져,
   정작 비용이 큰 재현 실행(다음 세션의 골든셋 재측정)에 아무 도움이 안 된다.
3. **`temperature=0.0`이 파이프라인 전 구간의 기본값이라 캐시가 의미론적으로
   안전하다.** 같은 입력에 같은 출력을 기대할 수 있다. `temperature > 0` 호출은
   캐시하지 않는다 — 샘플링 다양성을 캐시가 조용히 없애면 실험 결과가 달라진다.
4. **기본을 끄는 것이 이 프로젝트의 목적에 맞다.** 캐시는 측정 왜곡 요인이다.
   켜는 쪽에 명시적 행위를 요구하면, 측정 결과를 볼 때 "캐시가 켜져 있었나"를
   의심할 필요가 없어진다.
5. **프롬프트 버전을 키에 따로 넣지 않는다.** 프롬프트가 바뀌면 메시지 본문이
   바뀌고 키가 자동으로 달라진다. 별도 필드로 중복해 넣으면 두 곳이 어긋날
   여지만 생긴다.

## Evidence

- **Benchmark:** 골든셋 9건(`docs/eval/golden-set.json`), 코퍼스 16건, 임베딩 모델
  워밍업 후 상주 프로세스에서 측정. 원자료는 `docs/eval/bench-*.json`.

  | 조건 | 평균 파이프라인 지연 | p95 | 평균 LLM 지연 | 청구 토큰/요청 | 캐시 적중 |
  | --- | ---: | ---: | ---: | ---: | ---: |
  | 캐시 OFF | 17.43s | 37.29s | 15.76s | 11,095 | 0 / 109 |
  | 캐시 ON (콜드) | 14.36s | 29.32s | 13.17s | 10,069 | 17 / 109 |
  | 캐시 ON (웜) | 0.36s | 0.64s | 0.00s | 0 | 109 / 109 |

- **Experiment:** 캐시가 **비어 있는** 상태의 실행에서도 17/109(15.6%)가 적중했다.
  재검색 루프가 동일한 프롬프트를 반복한다는 직접 증거이며, 이 중복만으로도
  청구 토큰이 요청당 11,095 → 10,069(-9.2%)로 줄었다.
- **Cost:** 현 엔드포인트는 이미 할당된 무료 자원이라 **실제 금전 비용은 0원**이다.
  따라서 비용 지표는 금액이 아니라 **청구 토큰 수**로 센다 — 자원이 유료로 전환되거나
  2026년 말 만료 후 대체 경로로 옮길 때(ADR-003) 그대로 금액으로 환산할 수 있는 단위다.

## Alternatives

### 캐시를 두지 않는다 (현행 유지)

- **Pros:** 측정이 항상 실제 호출을 반영한다. 코드가 늘지 않는다.
- **Cons:** 같은 실행 안의 중복 호출(15.6%)까지 그대로 비용이 된다. 재현 실행이
  매번 전액 비용을 낸다.
- **Rejected because:** 중복이 실측으로 확인됐고, 데코레이터 한 겹으로 측정을
  왜곡하지 않으면서 제거할 수 있기 때문이다.

### LiteLLM 내장 캐시를 쓴다

- **Pros:** 코드를 거의 쓰지 않아도 된다.
- **Cons:** 캐시 동작이 LiteLLM 전역 설정(`litellm.cache`)에 묶여 프로바이더
  인스턴스 단위로 켜고 끌 수 없다. 측정 스크립트가 한 프로세스에서 두 조건을
  비교하기 어려워진다. 캐시 키 구성과 적중 통계도 우리가 통제하지 못해
  `billed_tokens` 같은 지표를 만들 수 없다.
- **Rejected because:** ADR-003이 LiteLLM을 고른 이유는 "교체 지점을 한 곳으로
  모으기 위함"이지 기능을 위임하기 위함이 아니다. 캐시까지 벤더에 위임하면
  LiteLLM 교체 비용이 다시 올라간다.

### Redis 등 공유 캐시를 쓴다

- **Pros:** 여러 프로세스·여러 워커가 캐시를 공유한다.
- **Cons:** 새 인프라 구성 요소가 생기고, 기동·운영·백업이 따라온다. 현재는
  단일 프로세스 실행이라 공유할 대상이 없다.
- **Rejected because:** 배포 형태가 아직 정해지지 않았다. 지금 고르면 배포 결정을
  캐시가 앞질러 정하게 된다.
- **Recheck if:** 세션 7에서 클라우드 배포 형태가 정해져 여러 워커가 같은
  캐시를 공유해야 할 때.

## Consequences

### Positive

- 재현 실행(골든셋 재측정, 데모, 문서 작성)이 사실상 공짜가 된다 — 웜 캐시에서
  파이프라인 평균 0.36초.
- 캐시를 켠 채로도 같은 실행 안의 중복 호출이 제거되므로, 재검색 루프를 고치기
  전까지의 **임시 완충**이 된다.
- `billed_tokens` 구분이 생겨, 비용 지표가 "요청한 토큰"이 아니라 "실제로 처리된
  토큰"을 가리키게 됐다.

### Negative

- 캐시를 켠 상태의 측정값은 파이프라인 성능이 아니라 캐시 적중률을 잰 것이다.
  조건을 표에 함께 적지 않으면 오해를 부른다. `bench_golden.py`가 조건 이름을
  결과 파일에 함께 쓰는 이유다.
- 프롬프트를 고치면 캐시 전체가 무효가 된다. 이것은 의도한 동작이지만, 프롬프트
  수정 직후의 첫 실행은 캐시 이전과 같은 비용을 낸다.

### Risks

- **캐시가 오래된 답을 돌려준다.** 코퍼스가 바뀌어 검색 결과가 달라지면 프롬프트도
  달라지므로 키가 자동으로 바뀐다. 다만 **인덱스는 그대로인데 모델 쪽이 바뀌는**
  경우(엔드포인트 교체, vLLM 재배포로 인한 동작 변화)는 키에 잡히지 않는다. 모델
  버전이 실제로 바뀌면 캐시를 비워야 한다(`clear_cache`).
- **적중률이 측정을 조용히 오염시킨다.** 기본을 꺼두는 것으로 1차 방어했지만,
  `.env`에 `LLM_CACHE=1`을 남겨두고 잊으면 같은 문제가 난다. 측정 스크립트가
  조건을 출력·기록하게 해 2차 방어했다.

## Reversibility

- **Reversible:** Yes
- **Rollback:** `get_provider()`가 기본으로 캐시 없는 프로바이더를 돌려주므로,
  되돌리려면 `src/providers/cache.py`와 `CacheSettings`를 지우고 `get_provider`의
  `cache` 인자를 제거하면 된다. 노드·그래프 코드는 손대지 않는다 — 데코레이터로
  둔 이유가 이것이다. `var/llm_cache/`는 커밋되지 않으므로 삭제만 하면 흔적이 없다.
- **Migration Cost:** Low

## Review Trigger

- 세션 7에서 클라우드 배포 형태가 정해져 여러 워커가 같은 캐시를 공유해야 할 때
  → Redis 등 공유 캐시를 다시 검토한다.
- `var/llm_cache/` 크기가 운영에 부담이 될 때 → 상한·만료 정책을 정한다.

## AI/ML Details

- **Model:** `gemma-4-31B-it` 고정 (ADR-002 모델 고정 원칙). 캐시는 모델을 바꾸지
  않으며, 캐시 키에 모델 이름이 들어가 있어 모델이 바뀌면 자동으로 미스가 된다.
- **Evaluation:** 골든셋 9건에서 캐시 온/오프 간 **채점 결과가 동일**했다
  (8 pass / 1 fail). 캐시가 출력을 바꾸지 않는다는 것을 확인한 것이다.
- **Inference:** 캐시 적중 시 엔드포인트 요청이 발생하지 않는다. 적중 응답의
  `latency_s`는 0, `billed_tokens`는 0이며, 원래 지연은 `origin_latency_s`에 남는다.
