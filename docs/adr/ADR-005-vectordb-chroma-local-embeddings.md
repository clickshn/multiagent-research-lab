# ADR-005: VectorDB는 Chroma로 시작하고 임베딩은 로컬 모델로 내린다

- **Status:** Proposed
- **Date:** 2026-09-15
- **Decision:** 벡터 저장소는 Chroma 임베디드 모드로 시작하고, 임베딩은 서빙 엔드포인트가 제공하지 않으므로 로컬 sentence-transformers(`intfloat/multilingual-e5-small`)로 계산한다.
- **Scope:** multiagent-research-lab (검색 계층 — 벡터 저장소 + 임베딩)
- **Decision Source:** Human

## Amendment 2 — 2026-09-18 (session-13): 간격 0.074는 **negative 1건으로 잰 값이었다**

> **목표를 바꾸는 것이 아니라 무엇을 재고 있었는지를 정정한다.**
> 아래 §4와 Evaluation 표의 `0.074`는 틀린 계산이 아니다. **대표성이 없는 표본이었다.**

### 무엇이 잘못 잡혀 있었나

§4는 "완전 무관과 정답의 간격"을 **GS-008 한 건**으로 정의했다. 당시 골든셋의
negative가 GS-008·GS-009 2건뿐이었고, 그 중 §4가 고른 것은
**「한국 개인정보보호법」 — 코퍼스와 주제가 전혀 겹치지 않는 극단값**이다.

session-13에서 골든셋을 30건으로 확대하며 **negative를 2 → 7건으로 늘리고
5건을 전부 근접 negative(주제는 가까운데 답은 없는 질의)로 채웠다.** 그러자:

| 무엇과의 간격인가 | negative 최고점 (ko) | **간격** (vs GS-005 정답 0.8401) |
|---|---:|---:|
| GS-008 "완전 무관" (§4의 원래 정의) | 0.7829 | **0.0572** |
| negative 7건 **평균** | 0.8133 | 0.0268 |
| **최난도 negative (GS-028)** | **0.8303** | **0.0098** |

**표본을 2 → 7건으로 늘렸더니 간격이 83% 줄었다.**
0.074(코퍼스 16건) → 0.0575(코퍼스 37건, session-12)라는 감소도 실재하지만,
**그 두 수치는 애초에 가장 쉬운 negative 하나로 잰 상한값이었다.**

### 더 중요한 귀결 — 절대 점수 임계값은 성립하지 않는다

최난도 negative의 최고점(0.8303)을 임계값으로 놓으면
**positive 23건 중 14건의 정답 문서 점수가 그 아래다.**
그중 **GS-013·GS-017(1위), GS-018(2위), GS-021·GS-011(3위)은 검색에 성공한 케이스**다 —
순위로는 맞히는데 점수는 무관 질의보다 낮다.

> §4의 "고정 유사도 임계값을 도입하면 질의 언어에 따라 다르게 동작한다"는 경고는
> **과소평가였다.** 언어에 따라 다르게 동작하는 정도가 아니라, **같은 언어 안에서도
> 정답과 오답의 점수 구간이 겹친다.** 근거 유무 판정은 **질의 내부 순위로만** 가능하다.

### 무엇이 그대로 유효한가

- **§4의 진단 자체는 옳고, 오히려 강화됐다.** "모든 문서가 모든 질의에 비슷하게 유사하다"는
  결론은 근접 negative를 넣자 더 분명해졌다.
- **"임베딩 모델 교체의 판단 기준은 재현율이 아니라 점수 간격"이라는 §6-2도 유효하다.**
  다만 **어느 negative로 재는지를 함께 적어야 한다** — 이 Amendment 이후로는
  `probe_retrieval.py`가 negative 7건의 최고점을 전건 기록한다(`negatives_top_score`).
- ADR-009 §, ADR-011, ADR-012가 인용한 `0.074`는 **코퍼스 16건 · negative 1건 기준값**으로
  읽는다. 수치를 일괄 치환하지 않는다 — 각 ADR이 그 시점의 측정을 인용한 것이기 때문이다.

### 후속

- 📌 **Verifier·Researcher의 점수 사용처 점검** (session-13 §6.2). 확인 결과
  **Verifier는 점수를 쓰지 않는다**(인용 개수 기계 판정 + LLM verdict). 그러나
  **Researcher 후보 프롬프트는 `유사도 0.xxx`를 모델에게 그대로 보여준다**
  (`_format_candidates`). 그 절대값이 위와 같이 오도적이므로 노출 방식을 재검토한다.
- 📌 이 Amendment는 **Evaluation 표의 목표 행을 고치지 않는다.** "간격은 클수록 좋다"는
  방향은 그대로다. 바뀐 것은 **그 간격을 무엇으로 재느냐**다.

## Amendment — 2026-09-16 (session-05): 크로스링구얼은 GS-006 실패의 원인이 아니다 (가설 기각)

session-04에서 **GS-006 실패가 코퍼스 부족이 아니라 검색 재현율 문제**로 좁혀졌다.
이 ADR의 Risks에 적어 둔 "교차 언어 검색 품질을 아직 측정하지 않았다"가 유력한 후보였다.
session-05에서 진단만 수행했다 (**코드·모델 변경 없음**. 기존 인덱스와 기존 `ChromaRetriever`를
그대로 쓰는 읽기 전용 프로브).

### 1. 골든셋만으로는 비교가 불가능하다 — 대조군이 없다

| 구분 | 건수 | 크로스링구얼(한국어 질의 ↔ 영어 문서) | 동일 언어 |
| --- | ---: | ---: | ---: |
| 실패 | **1** (GS-006) | 1 / 1 = **100%** | 0 |
| 통과 | 8 | 8 / 8 = **100%** | 0 |
| 전체 | 9 | 9 / 9 = **100%** | **0** |

골든셋 9건의 `language`가 전부 `ko`이고, 코퍼스 16건은 **한글이 한 글자도 없는 영어 문서**다
(`data/corpus/arxiv/*.json` 전수 확인). 즉 크로스링구얼은 **변수가 아니라 상수**다.
실패군과 통과군의 비율이 똑같이 100%이므로 **이 값으로는 실패를 전혀 설명할 수 없다.**

> 세션 지시는 "실패한 케이스들"의 비율을 세라는 것이었으나, 실측 결과 **실패는 GS-006 1건뿐**이다
> (`docs/eval/bench-no-cache.json` → `scoring.failed = 1`). n=1이라 비율 비교는 성립하지 않는다.

### 2. 그래서 대조군을 만들어 직접 쟀다 — 같은 질의의 영어 번역

같은 인덱스에 **동일한 질의의 영어 번역**을 넣어 기대 문서의 순위를 비교했다. 코퍼스가 영어이므로
영어 질의 = 동일 언어 조건이다. 번역은 초록의 표현을 베끼지 않고 질의의 의미만 옮겼다
(그렇지 않으면 어휘 일치로 유리해져 측정이 무의미해진다).

기대 문서 순위 (16건 코퍼스, 운영 설정은 `top_k=4`):

| 케이스 | 한국어 질의 순위 | 영어 질의 순위 | top-4 진입 (ko → en) |
| --- | ---: | ---: | --- |
| GS-001 | 3 | 1 | ✅ → ✅ |
| GS-002 | 1 | 1 | ✅ → ✅ |
| GS-003 | 1 | 1 | ✅ → ✅ |
| GS-004 | 3 | 3 | ✅ → ✅ |
| GS-005 | 1 | 1 | ✅ → ✅ |
| **GS-006** | **9** | **8** | **❌ → ❌** |
| GS-007 | 5 | 1 | ❌ → ✅ |

| 지표 (positive 7건) | 한국어 질의 | 영어 질의 |
| --- | ---: | ---: |
| top-4 재현율 | 5/7 = **71.4%** | 6/7 = **85.7%** |
| 기대 문서 평균 순위 | 3.29 | 2.29 |

### 3. 결론 — 두 가지를 분리해야 한다

**(a) 크로스링구얼이 재현율을 깎는 것은 사실이다.** 질의를 영어로 바꾸면 GS-007이 5위 → 1위,
GS-001이 3위 → 1위로 올라온다. top-4 재현율이 71.4% → 85.7%로 개선된다. 이 ADR의 Risks에
적어둔 우려는 **유효하며, 이제 수치가 있다.**

**(b) 그러나 GS-006은 그것으로 설명되지 않는다 — 가설 기각.** 동일 언어(영어) 질의에서도
기대 문서 `arXiv:2404.01023v1`은 16건 중 **8위**다. 크로스링구얼을 완전히 제거해도 top-4에
들어오지 못한다. **유일하게 실패한 케이스가 유일하게 번역으로 고쳐지지 않는 케이스다.**

`arXiv:2404.01023v1`의 제목은 *"Large Language Model Evaluation Via Multi AI Agents"*로
질의("LLM의 성능을 평가하기 위해 멀티에이전트 구조를 사용하는 접근")와 거의 일대일 대응한다.
제목이 사실상 질의의 번역인 문서조차 8위로 밀린다.

### 4. 더 그럴듯한 원인 — 임베딩 공간의 변별력 부족

프로브에서 드러난 코사인 유사도 분포:

| 관측 | 값 |
| --- | ---: |
| 한국어 질의, 1위와 4위의 점수 차 | 약 **0.009 ~ 0.013** |
| 코퍼스에 답이 **전혀 없는** 질의(GS-008, 한국 개인정보보호법)의 최고 점수 | **0.766** |
| 정답 문서를 1위로 맞힌 질의(GS-005)의 최고 점수 | 0.840 |
| → "완전 무관"과 "정답" 사이의 간격 | **0.074** |

**모든 문서가 모든 질의에 대해 비슷하게 유사하다.** 순위 1위와 4위가 0.01 차이로 갈리고,
주제가 완전히 다른 질의조차 0.77점을 받는다. 이 분포에서는 top-4 절단이 의미 차이가 아니라
노이즈로 결정된다. GS-006이 8~9위인 것도 "멀리 떨어져서"가 아니라 **모두가 붙어 있어서**다.

부수 관측: 영어 질의는 정답·오답을 가리지 않고 점수를 일괄 상향시킨다
(GS-009 negative 케이스도 0.824 → 0.851). **고정 유사도 임계값을 도입하면 질의 언어에 따라
다르게 동작한다** — 임계값 방식을 검토할 때 반드시 고려해야 한다.

### 5. 이 프로브의 한계 (과대 해석 금지)

- **파이프라인과 검색어가 다르다.** 프로브는 골든셋의 *케이스 질의*를 그대로 넣었지만, 실제
  파이프라인은 Outliner가 만든 *소주제*로 `f"{query} {topic}"` 형태의 검색을 4~8회 돈다
  (ADR-006 Amendment). 따라서 위 순위는 파이프라인 재현율의 **대리 지표**이지 동일 값이 아니다.
  GS-007이 프로브에서 5위인데 골든셋은 통과한 것이 그 차이다.
- **n=7, 코퍼스 16건.** 71.4% vs 85.7%는 케이스 1건 차이다. 경향의 방향은 일관되지만
  크기를 신뢰할 표본이 아니다.
- **번역은 사람(에이전트) 1회 작성본**이며 번역 품질이 교란 변수로 남아 있다.

### 6. 후속 (이번 세션 범위 밖 — 지시에 따라 수정하지 않음)

1. **골든셋에 영어 질의 케이스를 추가해 대조군을 상설화한다.** 지금 구조로는 언어 효과를
   영원히 측정할 수 없다. 이것이 가장 싸고 효과가 크다.
2. 임베딩 모델 교체 후보(`multilingual-e5-base`/`bge-m3`) 비교 — 판단 기준은 top-4 재현율이
   아니라 **정답과 무관 문서의 점수 간격**이어야 한다. 위 §4가 그 이유다.
3. GS-006 단독으로 리랭커 또는 어휘 검색(BM25) 하이브리드의 효과를 확인한다. 순위 8위는
   의미 검색만으로는 top-4에 못 들어오지만 제목 어휘 일치로는 1위가 될 가능성이 높다.

**재현:** 위 수치는 `var/chroma/` 인덱스(`intfloat/multilingual-e5-small`, 16건)에
읽기 전용 검색을 돌려 얻었다. LLM 엔드포인트를 호출하지 않는다 (임베딩은 로컬).

## Context

### Problem

session-02 핸드오프에서 **VectorDB 선택이 Researcher 노드 구현을 막고 있는 항목**으로
기록됐다. 검색 결과에 문서 ID와 문서 내 위치가 항상 함께 와야 한다는 요구(출처 제시,
`docs/problem-statement.md` §3 목표 2)가 후보 선정의 1순위 기준이다.

여기에 더해, 임베딩을 어디서 계산할지가 정해지지 않았다. 추론은 KT Cloud AI Nexus의
vLLM 엔드포인트로 하고 있는데, 같은 엔드포인트가 임베딩도 서빙하는지 확인되지 않은
상태였다. 서빙한다면 임베딩 계산도 그쪽에 맡기는 것이 단순하다.

### Constraints

- 검색 결과에 `doc_id`와 `locator`가 항상 실려야 한다. 이게 안 되는 후보는 탈락이다.
- 이번 세션의 목표는 "동작 확인"이다. 별도 서버를 세우고 운영해야 하는 선택지는
  이번 세션 안에 끝나지 않는다.
- 외부 LLM 벤더 비의존 — 문서 내용이 타사 모델로 나가면 안 된다. 관리형 임베딩 API는
  이 제약에 걸린다.
- 세션 6에서 컨테이너화가 예정돼 있어, 그 시점에 저장소 형태를 다시 볼 기회가 있다.
- 대상 문서가 한국어·영어 혼재 환경이다 (`docs/problem-statement.md` §3 비목표).

## Decision

### Selected

- **Technology:** Chroma 1.5.5 (임베디드 PersistentClient) + sentence-transformers 5.1.1 (`intfloat/multilingual-e5-small`)
- **Architecture:** 노드는 `src/tools/retrieval.py`의 `Retriever` 프로토콜만 본다. 임베딩은 `src/providers/embeddings.py`의 `EmbeddingProvider` 프로토콜 뒤에 둔다. **두 결정은 서로 묶지 않는다** — Chroma의 기본 임베딩 함수를 쓰지 않고 우리가 계산한 벡터를 직접 넣는다. 그래야 벡터 DB 교체와 임베딩 모델 교체를 따로 되돌릴 수 있다.
- **Implementation:** 인덱스는 `var/chroma/`에 두고 커밋하지 않는다. 커밋 대상은 `data/corpus/`의 원본 스냅샷이며 `scripts/build_index.py`로 재생성한다. 컬렉션 메타데이터에 임베딩 모델 이름을 기록하고, 인덱스를 만든 모델과 현재 설정이 다르면 검색 시 예외를 던진다 — 모델이 바뀌면 벡터 공간이 달라져 에러 없이 결과만 이상해지는 조용한 실패가 나기 때문이다. 유사도는 코사인이며 임베딩을 정규화해서 넣는다.

## Rationale

1. **임베딩을 로컬로 내리는 것은 선택이 아니라 확인 결과다.** 엔드포인트의
   `/v1/embeddings`가 404를 반환한다(아래 Evidence). 현 서빙 경로는 생성 전용이므로
   임베딩은 다른 곳에서 계산해야 한다.
2. **로컬 임베딩은 벤더 비의존 제약을 깨지 않는다.** 모델 가중치가 로컬에 있고 문서
   내용이 어디로도 나가지 않는다. 판단 기준은 네트워크 도달 가능성이 아니라 데이터가
   향하는 곳이다 (`docs/problem-statement.md` §2).
3. **Chroma는 임베디드라 이번 세션 안에 붙는다.** 별도 서버 프로세스·컨테이너·접속
   설정이 없고 디스크 경로 하나면 된다. "동작 확인"이 목표인 단계에서 인프라 작업이
   선행되지 않는 것이 결정적이다.
4. **Chroma는 메타데이터를 문서와 함께 저장·반환한다.** `doc_id`·`locator`를 메타데이터로
   실어 검색 결과에 항상 함께 오게 할 수 있다 — 1순위 기준을 만족한다.
5. **다국어 모델이어야 한다.** 질의는 한국어, 문서(arXiv 초록)는 영어인 교차 언어 검색이
   기본 상황이다. `multilingual-e5-small`은 118M 파라미터로 CPU에서 돌아갈 만큼 가볍고
   한국어·영어를 같은 벡터 공간에 둔다.
6. **세션 6에 재검토 기회가 이미 있다.** 지금 서버형 DB를 고르면 이번 세션의 비용이
   커지는데, 컨테이너화 시점에 어차피 저장소 배치를 다시 봐야 한다. 그때 판단하는 것이
   정보가 더 많은 상태에서의 결정이다.

## Alternatives

### Qdrant

- **Pros:** 필터링·스케일 특성이 좋고 운영 환경에 적합하다. 컨테이너 배포가 표준적이다.
- **Cons:** 별도 서버 프로세스가 필요해 이번 세션에 인프라 작업이 선행된다.
- **Rejected because:** 이번 세션의 목표가 "동작 확인"이라, 서버를 세우는 비용이 목표 달성을 지연시킨다.
- **Recheck if:** 세션 6 컨테이너화 시점 — 그때 Qdrant로 옮길지 별도 ADR로 다시 판단한다.

### FAISS

- **Pros:** 검색 속도가 빠르고 의존성이 가볍다.
- **Cons:** 메타데이터 저장을 직접 관리해야 한다 — 벡터 인덱스와 문서 메타데이터를 따로 들고 다니며 동기화해야 한다.
- **Rejected because:** `doc_id`·`locator`가 항상 함께 와야 한다는 1순위 기준을 우리가 직접 구현해서 유지해야 하는데, 그 동기화가 깨지면 출처가 틀린 인용이 나온다.

### 엔드포인트의 임베딩 API 사용

- **Pros:** 임베딩 계산을 로컬에 두지 않아도 되고, 모델 관리 지점이 하나로 줄어든다.
- **Cons:** —
- **Rejected because:** 엔드포인트가 `/v1/embeddings`를 제공하지 않는다 (실측 404). 선택지가 아니다.
- **Recheck if:** 엔드포인트가 임베딩 서빙을 추가하는 경우 (`scripts/probe_embeddings.py`가 200을 반환).

### 관리형 임베딩 API (OpenAI 등)

- **Pros:** 품질이 좋고 운영 부담이 없다.
- **Cons:** 문서 내용이 타사 LLM 벤더로 전송된다.
- **Rejected because:** 외부 LLM 벤더 비의존이라는 핵심 제약에 정면으로 걸린다 (`docs/problem-statement.md` §2).

## Consequences

### Positive

- 별도 서버 없이 이번 세션 안에 Researcher 노드가 동작한다.
- 벡터 DB와 임베딩 모델을 따로 교체할 수 있다 — 한쪽을 고정하고 다른 쪽만 바꿔가며 측정하는 이 프로젝트의 측정 원칙과 맞는다.
- 임베딩 모델 불일치가 조용한 품질 저하가 아니라 예외로 드러난다.

### Negative

- `sentence-transformers`가 torch를 전이 의존성으로 끌고 온다. 의존성 트리가 눈에 띄게 넓어졌다 (검증 환경 torch 2.9.0).
- CPU 임베딩이라 코퍼스가 커지면 인덱싱 시간이 선형으로 늘어난다. 지금 규모에서는 문제가 아니지만 수천 건 단위에서는 다시 봐야 한다.
- Chroma 임베디드는 단일 프로세스 전제다. 여러 실행이 동시에 인덱스를 쓰는 상황은 지원 범위 밖이다.

### Risks

- **[측정됨 — session-05]** 교차 언어 검색(한국어 질의 → 영어 문서)이 재현율을 깎는다:
  top-4 재현율 ko 71.4% vs en 85.7% (n=7). 다만 **유일한 골든셋 실패(GS-006)는 이것으로
  설명되지 않는다** — 영어 질의에서도 8위다. 위 Amendment 참조.
- `multilingual-e5-small`은 경량 모델이라 도메인 용어에서 약할 수 있다. 검색 재현율이 목표에
  못 미치면 모델 교체(인덱스 재생성 필요)가 먼저 검토 대상이다.
  **[구체화 — session-05]** 실제 관측된 증상은 도메인 용어 약점보다 **점수 변별력 부족**이다.
  코퍼스에 답이 없는 질의도 0.77점을 받고, 1위와 4위가 0.01 차이로 갈린다. 교체 모델을
  고를 때의 기준은 재현율이 아니라 **정답과 무관 문서의 점수 간격**이어야 한다.

## Reversibility

- **Reversible:** Yes
- **Rollback:** 벡터 DB 교체는 `Retriever` 프로토콜을 구현한 클래스를 하나 더 쓰고 `scripts/build_index.py`를 다시 돌리면 된다 — 노드 코드는 바뀌지 않는다. 임베딩 모델 교체는 `.env`의 `EMBEDDING_MODEL`을 바꾸고 `--reset`으로 인덱스를 재생성한다. 원본 스냅샷이 `data/corpus/`에 커밋돼 있어 재생성에 외부 의존이 없다.
- **Migration Cost:** Low

## AI/ML Details

- **Model:** `intfloat/multilingual-e5-small` (118M, 384차원, 다국어). e5 계열은 질의에 `query: `, 문서에 `passage: ` 접두사를 요구하며, 이를 빠뜨리면 에러 없이 검색 품질만 나빠진다 — 접두사를 설정(`EmbeddingSettings`)으로 들고 다니고 모델 이름에 `e5`가 없으면 자동으로 끈다.
- **Evaluation:** 골든셋 확보 후 검색 재현율 측정 예정. 현재는 기준선 없음.
- **Inference:** CPU, 정규화된 임베딩 + 코사인 유사도. 조사 항목당 기본 top-k=4.
