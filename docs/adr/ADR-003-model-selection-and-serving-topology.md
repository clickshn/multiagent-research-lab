# ADR-003: 모델 선택 및 서빙 구성 — 기존 KT Cloud AI Nexus vLLM 엔드포인트 재사용

- **Status:** Proposed
- **Date:** 2026-09-15
- **Decision:** 로컬에서 vLLM을 새로 구축하지 않고, 이미 KT Cloud AI Nexus에 배포·운영 중인 vLLM 엔드포인트(`gemma-4-31B-it`)를 OpenAI 호환 API로 재사용한다.
- **Scope:** multiagent-research-lab (모델 서빙 계층 + 프로바이더 추상화)
- **Decision Source:** Human
- **Amended:** 2026-09-15 (session-04) — 접근 가능한 엔드포인트가 하나뿐이라 모델 라우팅
  실험을 보류한다는 사실을 기록 (아래 Amendment 참조).

---

## Amendment — 2026-09-15 (session-04): 단일 엔드포인트라 모델 라우팅 실험은 보류

**단일 엔드포인트라 모델 라우팅 실험은 이번 범위에서 보류한다. LiteLLM 추상화는 이미
있으니 엔드포인트가 추가되면 바로 시도 가능하다.**

- KT Cloud AI Nexus에서 우리가 접근할 수 있는 모델은 `gemma-4-31B-it` 하나다
  (`GET /v1/models` 실측 — session-03 `scripts/probe_embeddings.py`). 같은 엔드포인트가
  `/v1/embeddings`를 제공하지 않아 임베딩을 로컬로 내린 것도 같은 제약의 결과다 (ADR-005).
- 따라서 "쉬운 단계는 작은 모델, 어려운 단계는 큰 모델"과 같은 **단계별 모델 라우팅은
  비교 대상 자체가 없어** 이번 범위에서 수행할 수 없다. 못 한 실험을 한 것처럼 적지 않는다.
- **전환 준비는 이미 돼 있다.** 본 ADR이 정한 LiteLLM 프로바이더 계층(`src/providers/`)이
  모델 식별자와 엔드포인트를 `ProviderSettings` 한 곳에 모아두므로, 두 번째 엔드포인트가
  생기면 노드 코드를 고치지 않고 프로바이더 인스턴스를 나눠 주는 것만으로 라우팅을
  시도할 수 있다. 캐시를 데코레이터로 붙인 것(ADR-008)이 같은 확장 지점이 실제로
  동작한다는 예시다.
- 이 보류는 **모델 고정 원칙(ADR-002)과 충돌하지 않는다.** 모델 고정은 하네스 효과를
  분리해 측정하기 위한 것이고, 라우팅 실험은 그 측정이 끝난 뒤 별도 변인으로 다룰 주제다.
  현재는 선택의 여지가 없어 자동으로 고정돼 있을 뿐이다.

## Context

### Problem

ADR-002는 서빙 *계층*으로 vLLM을 정했지만, **어떤 모델을 쓸지**와 **그 vLLM을 누가
어디서 기동할지**는 열어두었다. session-01의 열린 이슈 목록에서도 "구체 모델 선택"과
"GPU 전용 여부"가 가장 시급한 확인 사항으로 남아 있었다.

Outliner / Researcher / Writer 골격을 작성하려면 실제로 호출 가능한 엔드포인트가 필요하다.
서빙 경로가 정해지지 않으면 노드 함수의 모델 호출부를 작성할 수 없고, 계측(지연·토큰)의
기준선도 잡을 수 없다.

### Constraints

- 외부 SaaS LLM API(OpenAI/Anthropic 등)를 쓸 수 없다. 사내 문서 내용이 타사 LLM 벤더로
  나가지 않아야 한다 — 자체 호스팅 오픈소스 모델만 허용된다 (`docs/problem-statement.md` §2).
- 가용 GPU가 제한적이며, 자체 기동 시 GPU 확보·드라이버·CUDA/torch 버전 고정·모델 가중치
  반입까지 우리가 떠안아야 한다.
- 현재 사용 가능한 KT Cloud AI Nexus 엔드포인트는 **정부지원 GPU 자원 할당으로 무료**이며
  **2026년 말까지만 유효**하다.
- 엔드포인트 URL은 사내 전용 정보라 레포에 커밋할 수 없다.

## Decision

### Selected

- **Technology:** KT Cloud AI Nexus에 배포된 vLLM 엔드포인트, 모델 `gemma-4-31B-it` (OpenAI 호환 `/v1` API)
- **Architecture:** 서빙은 우리 시스템 경계 **바깥**의 기존 인프라에 둔다. 우리 쪽은 클라이언트만 구현하며, 모든 모델 호출은 LiteLLM 기반 프로바이더 추상화 계층(`src/providers/`)을 통과한다. Orchestrator와 Sub-agent는 엔드포인트 URL·모델 이름·프로바이더 종류를 알지 못하고, 추상화 계층이 노출하는 인터페이스에만 의존한다.
- **Implementation:** 엔드포인트 주소와 모델 이름은 `.env`의 `VLLM_BASE` / `VLLM_MODEL`로 주입하고 코드에 고정하지 않는다. 레포에는 `.env.example`에 키 이름과 플레이스홀더만 커밋한다. LiteLLM에는 OpenAI 호환 커스텀 엔드포인트(`openai/<model>` + `api_base`) 형태로 설정한다.

## Rationale

1. **이미 검증된 인프라를 재사용한다.** 엔드포인트가 이미 배포되어 동작 중이므로, GPU 확보·
   vLLM 설치·모델 가중치 반입·기동 파라미터 튜닝 단계를 전부 건너뛴다. 세션 2에서 바로
   실제 추론 호출이 가능한 상태가 되어, 오케스트레이터 골격 작업이 가정 위가 아니라
   동작하는 엔드포인트 위에서 진행된다.
2. **인프라 관리 부담을 회피한다.** 자체 기동은 CUDA/torch 버전 고정, GPU 메모리 선점
   (`gpu_memory_utilization`), 장애 시 복구, 업그레이드 절차를 모두 우리 책임으로 만든다.
   이 프로젝트의 목표는 하네스(오케스트레이션 구조·검증 루프·컨텍스트 관리) 품질을
   측정하는 것이지 서빙 인프라를 운영하는 것이 아니다. 관리 부담을 덜어낸 만큼 하네스
   작업에 자원을 쓴다.
3. **제약 위반이 아니다.** 이 엔드포인트는 외부 인터넷에서 도달 가능한 HTTPS 프록시지만,
   우리가 통제하는 자체 호스팅 오픈소스 모델을 서빙한다. 핵심 제약은 "인터넷 차단"이 아니라
   "데이터가 타사 LLM 벤더로 나가지 않는 것"이며, 이 구성은 그 제약을 만족한다
   (`docs/problem-statement.md` §2).
4. **ADR-002의 서빙 선택을 뒤집지 않는다.** 서빙 계층은 여전히 vLLM이다. 바뀐 것은
   인스턴스를 누가 기동하는가뿐이며, 오케스트레이션 코드는 OpenAI 호환 API 뒤에 있어
   영향을 받지 않는다. 동시에 ADR-002에서 열어둔 "로컬 기동 시 GPU 메모리 선점" 재검토
   조건은 전제가 사라져 해소된다.
5. **교체 비용을 미리 낮춘다.** 자원이 2026년 말 만료된다는 것을 알고 시작하므로, 처음부터
   모델 호출을 프로바이더 추상화 뒤에 두어 엔드포인트 교체가 설정 변경으로 끝나게 만든다.
   만료가 리스크가 아니라 예정된 설정 변경이 되도록 설계하는 것이다.

## Evidence

- **Production Data:** 2026-09-15 세션 2에서 실제 엔드포인트에 헬스체크 2회 수행.
  - `GET /v1/models` → HTTP 200, 7.80s (콜드 커넥션, TLS 핸드셰이크 포함).
    응답으로 모델 ID `gemma-4-31B-it`, `max_model_len` 262144, `owned_by: vllm` 확인.
  - `POST /v1/chat/completions` (`max_tokens=16`, `temperature=0`) → HTTP 200, 0.152s
    (웜 커넥션, `time_connect` 0.017s). `finish_reason: stop`, usage
    `prompt_tokens=18 / completion_tokens=2 / total_tokens=20`. 응답 본문 정상.
  - 인증 헤더 없이 200 응답 — 현재 엔드포인트는 API 키를 요구하지 않는다.
- **Cost:** 0원. 정부지원 GPU 자원 할당분으로 2026년 말까지 무료.

## Alternatives

### 로컬에 vLLM을 신규 구축 (session-01까지의 전제)

- **Pros:** 서빙 인프라를 완전히 통제한다. 외부 할당 자원의 유효기간에 묶이지 않고,
  모델·양자화·배치 파라미터를 자유롭게 바꿀 수 있다. 네트워크 경계 안에서 끝나므로
  망분리 요건이 강화되어도 대응된다.
- **Cons:** GPU 확보가 선행되어야 하고, CUDA/torch 버전 고정 때문에 오프라인 설치가
  까다롭다. 모델 가중치 반입 절차, 기동 파라미터 튜닝, 장애 복구·업그레이드가 전부
  우리 운영 부담이 된다. GPU를 다른 워크로드와 공유할 경우 vLLM의 메모리 선점이 충돌한다.
- **Rejected because:** 동일한 결과(vLLM으로 서빙되는 오픈소스 모델)를 이미 검증된 채로
  즉시 얻을 수 있는데, 같은 것을 다시 만들면서 인프라 관리 부담까지 떠안을 이유가 없다.
  하네스 품질 측정이라는 프로젝트 목표에 기여하지 않는 작업이다.
- **Recheck if:** 2026년 말 정부지원 GPU 자원 할당이 만료되기 전 — 대체 엔드포인트를
  검토해야 하며, 그 선택지 중 하나가 자체 기동이다.

## Consequences

### Positive

- **LiteLLM 추상화 덕분에 엔드포인트 교체 시 Orchestrator / Sub-agent 코드 변경이
  불필요하다.** 엔드포인트·모델이 바뀌어도 `.env` 값과 프로바이더 계층 설정만 손대면 되고,
  그래프 정의와 노드 함수는 그대로다. 2026년 말 전환이 코드 변경이 아닌 설정 변경이 된다.
- GPU 확보·vLLM 설치·가중치 반입 단계가 사라져, 세션 2에서 바로 동작하는 엔드포인트 위에서
  오케스트레이터 골격을 작성할 수 있다.
- 서빙 비용이 0원이라 초기 실험·골든셋 측정 단계에서 호출 횟수를 비용 때문에 아끼지 않아도 된다.
- 컨텍스트 길이가 262144 토큰이라, 근거 문서를 다수 주입하는 Researcher → Writer 경로에서
  당분간 컨텍스트 예산이 병목이 되지 않는다.

### Negative

- 서빙 인프라를 우리가 운영하지 않으므로, 모델 교체·양자화·배치 파라미터 같은 서빙 측
  튜닝 여지가 없다. 처리량이 부족해도 우리 쪽에서 조정할 수단이 제한적이다.
- 모델이 `gemma-4-31B-it`로 사실상 고정된다. 모델 비교 실험을 하려면 별도 서빙 경로가 필요하다.
  (다만 ADR-002의 "모델 고정 원칙"과는 오히려 부합한다.)
- 엔드포인트가 HTTPS 프록시 경유라, 완전한 사내 망분리가 요구사항으로 격상되면 이 구성을
  그대로 쓸 수 없다.

### Risks

- **정부지원 GPU 자원 할당이 2026년 말 만료된다.** 만료 후 이 엔드포인트는 사용할 수 없으며,
  대체 서빙 경로(자체 GPU 기동 / 다른 할당 자원 / 유료 전환)로 전환해야 한다. 전환 계획 없이
  만료를 맞으면 시스템 전체가 멈춘다. 프로바이더 추상화로 전환 비용은 낮췄으나,
  **대체 경로 확보 자체는 여전히 해결되지 않은 과제다.**
- 가용성·지연이 외부 통제 하에 있다. 엔드포인트 장애 시 우리 쪽에 복구 수단이 없고,
  다른 사용자와 자원을 공유한다면 부하에 따라 지연이 변동할 수 있다. 계측 시 이 변동이
  하네스 변경의 효과와 섞이지 않도록 기준선을 반복 측정해야 한다.
- 현재 인증이 없어 엔드포인트 URL을 아는 누구나 호출할 수 있다. URL을 사내 전용 정보로
  취급해 커밋 금지로 관리하지만, 이는 접근 통제가 아니라 노출 억제일 뿐이다.

- [x] 엔드포인트 헬스체크 (`/v1/models`, `/v1/chat/completions`) 성공 확인
- [x] LiteLLM 기반 프로바이더 추상화 계층 (`src/providers/`) 추가

- [ ] Langfuse 계측 연동으로 엔드포인트 지연 기준선 반복 측정
- [ ] 2026년 말 전 대체 서빙 경로 확보 계획 수립

## Reversibility

- **Reversible:** Yes
- **Rollback:** 모델 호출이 LiteLLM 프로바이더 계층 뒤에 있으므로, `.env`의 `VLLM_BASE` /
  `VLLM_MODEL`을 다른 OpenAI 호환 엔드포인트로 바꾸면 된다. Orchestrator / Sub-agent 코드는
  변경하지 않는다. 자체 vLLM 기동으로 되돌리는 경우에도 클라이언트 쪽 변경은 동일하게
  설정 수준이며, 비용은 서버 쪽 구축(GPU 확보·설치·가중치 반입)에 집중된다.
- **Migration Cost:** Low (클라이언트 관점) / Medium~High (자체 기동으로 전환 시 서버 구축 포함)

## Review Trigger

- **접근 가능한 엔드포인트가 2개 이상이 되면** 단계별 모델 라우팅 실험을 다시 검토한다 (session-04 Amendment). 프로바이더 계층이 이미 교체 지점을 모아두었으므로 노드 코드 변경 없이 시도할 수 있다.

- **2026년 말 정부지원 GPU 자원 할당 만료 전 대체 엔드포인트 검토 필요.** 만료 시점에
  쫓기지 않도록 여유를 두고 시작하며, 검토 선택지는 자체 vLLM 기동 / 다른 할당 자원 /
  유료 전환이다. 자체 기동을 선택하면 ADR-002에서 해소 처리한 "vLLM GPU 메모리 선점"
  이슈가 다시 유효해지므로, ADR-002의 Amendment를 함께 참조한다.

## AI/ML Details

- **Model:** `gemma-4-31B-it` — 지시 튜닝(instruction-tuned) 오픈소스 모델, vLLM으로 서빙.
  컨텍스트 길이 262144 토큰 (엔드포인트 `max_model_len` 실측). 모델은 고정하고 하네스만
  바꿔가며 측정한다 (ADR-002 모델 고정 원칙).
- **Evaluation:** 골든셋 미구축 상태라 품질 지표는 아직 측정하지 않았다. 지표 정의는
  `docs/problem-statement.md` §4에 있으며 목표값은 골든셋 확정 후 채운다.
- **Inference:** OpenAI 호환 `/v1/chat/completions`. 호출은 LiteLLM 프로바이더 계층을 경유하며,
  엔드포인트·모델은 `.env`로 주입한다. 현재 인증 헤더 불필요. 최소 요청 왕복 0.152s 실측
  (웜 커넥션, 출력 2토큰) — 실제 에이전트 워크로드의 지연 기준선은 계측 연동 후 별도 측정한다.
