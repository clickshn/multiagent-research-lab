# ADR-006: 검증 루프의 되돌림 조건은 기계 판정 + 모델 판정 2단계로 정한다

- **Status:** Proposed
- **Date:** 2026-09-15
- **Decision:** Verifier는 인용 수를 세는 기계 판정으로 먼저 거르고, 인용이 붙은 항목만 모델에게 정합성을 묻는다. 판정에 실패하거나 애매한 항목은 통과시키지 않고 Researcher로 되돌린다. 되돌림은 `max_revisions`(기본 2)에서 멈춘다.
- **Scope:** multiagent-research-lab (오케스트레이터 — 검증 루프)
- **Decision Source:** Human

---

## Context

### Problem

그래프 골격은 session-02에서 `verifier ⇄ researcher` 사이클로 배선됐지만, **언제
되돌리는가**는 비어 있었다. 이 조건이 이 시스템의 핵심 동작을 결정한다.

- 너무 느슨하면(근거가 있기만 하면 통과) 주제만 비슷한 문서가 인용으로 붙는다.
  검색은 의미 유사도로 동작하므로 "관련 있어 보이지만 그 주장을 뒷받침하지는 않는"
  문서가 항상 상위에 걸린다.
- 너무 빡빡하면 루프가 계속 돌고, 같은 질의를 반복해도 같은 검색 결과가 나오므로
  개선 없이 비용만 늘어난다.
- 판정 자체가 실패하는 경우(모델 호출 실패, 형식 위반)를 어떻게 다룰지도 정해야 한다.

이 프로젝트의 1순위 제약은 "근거를 찾지 못하면 문장을 만들지 않는다"이다
(`docs/problem-statement.md` §3 목표 2). 검증 조건은 이 제약을 구조적으로 강제하는
자리다.

### Constraints

- LLM 호출 1건당 지연과 토큰이 든다. 셀 수 있는 것을 모델에게 묻는 것은 낭비다.
- 재검색은 무한히 돌 수 없다 — 배치성 실행이라 종료가 보장되어야 한다.
- "왜 루프가 멈췄는가"를 그래프 정의만 보고 답할 수 있어야 한다 (ADR-002 Rationale 2).
- 감사 로그 요구상 판정 근거가 기록에 남아야 한다.

## Decision

### Selected

- **Technology:** LangGraph 조건부 엣지 + `src/orchestrator/nodes.py`의 `make_verifier_node` / `route_after_verify`
- **Architecture:** 판정을 2단계로 나눈다. (1) **기계 판정** — 항목에 붙은 인용이 `min_citations`(기본 1) 미만이면 모델을 부르지 않고 바로 `uncovered`. (2) **모델 판정** — 인용이 붙은 항목만, 그 근거가 실제로 항목을 뒷받침하는지 묻고 `covered`가 아니면 `uncovered`. 되돌림 여부 자체는 노드가 아니라 라우터(`route_after_verify`)가 State만 읽고 결정한다.
- **Implementation:** 판정 실패(모델 호출 실패, JSON 형식 위반)는 **통과가 아니라 `uncovered`로 처리한다.** Researcher는 재검색 시 `uncovered`에 남은 항목만 다시 다루고, 프롬프트에 "이전 시도에서 근거를 찾지 못했다"는 힌트를 덧붙여 검색 해석을 넓힌다. 인용은 `findings` reducer로 누적되므로 판정은 항목별로 지금까지 모인 근거 전체를 합쳐서 본다. 상한(`max_revisions`, 기본 2)에 도달하면 남은 항목은 "근거 없음"으로 표시된 채 Writer로 넘어간다.

## Rationale

1. **셀 수 있는 것을 모델에게 묻지 않는다.** 인용이 0개인 항목은 모델 판정이 필요 없다.
   기계 판정을 먼저 두면 호출 수와 지연이 줄고, 그만큼 판정이 결정적(deterministic)이
   되어 재현성 요구에도 맞는다.
2. **기계 판정만으로는 부족하다.** 검색은 의미 유사도라 주제만 비슷해도 걸린다. 인용이
   붙었다는 사실은 "무언가 찾았다"는 뜻이지 "그 주장을 뒷받침한다"는 뜻이 아니다.
   정합성 판정은 사람이 읽고 판단하던 부분이라 모델이 필요하다.
3. **판정 실패를 통과로 처리하면 검증 단계가 있으나 마나가 된다.** 모델이 응답하지
   않거나 형식을 어겼을 때 그냥 넘기면, 장애가 곧 품질 저하로 조용히 이어진다.
   보수적으로 `uncovered`에 넣으면 최악의 경우에도 "근거 없음"으로 표시될 뿐이다.
4. **상한이 없으면 종료가 보장되지 않는다.** 같은 인덱스에 같은 질의를 다시 던지면
   검색 결과가 거의 같아, 근거가 없는 항목은 몇 번을 돌아도 계속 없다. 상한 2회는
   "재검색이 한 번은 의미 있게 시도된다"와 "비용이 두 배를 넘지 않는다" 사이의 값이다.
5. **루프 종료 조건을 라우터 한 곳에 모은다.** 노드가 스스로 "이제 그만"을 결정하면
   종료 조건이 코드 여러 곳에 흩어진다. 라우터가 State만 읽고 판단하면 그래프 정의를
   보고 종료 조건을 답할 수 있다.

## Evidence

- **Experiment:** session-03 e2e 실행 2회 (코퍼스 16건)

  | 항목 | 근거 있는 질의<br/>`20260915-152557-c34630` | 근거 없는 질의(GS-008)<br/>`20260915-152711-81bcd7` |
  | --- | ---: | ---: |
  | 조사 항목 | 4개 | 4개 |
  | 최종 `covered` | 2개 | 0개 |
  | 최종 `uncovered` | 2개 (상한 도달) | 4개 (상한 도달) |
  | Researcher 호출 | 6회 | 8회 |
  | **Verifier 호출** | 6회 | **0회** |
  | 전체 소요 / 토큰 | 55.6s / 13,298 | 33.9s / 11,061 |

  → 루프가 실제로 되돌아갔고(재검색), 상한에서 멈췄으며, 근거를 못 찾은 항목은 초안에
  "근거 없음"으로 표시됐다. **근거 없는 질의에서 Verifier 호출이 0회**인 것이 기계 판정
  단계가 실제로 일한다는 직접 증거다 — 인용이 0개인 항목은 모델을 부르지 않고 걸러졌고,
  그만큼(3,336 토큰 / 8.62s) 아꼈다.

  다만 **재검색으로 근거를 새로 찾은 항목은 두 실행 모두 0건이다.** 아래 Risks 참조.

## Alternatives

### 인용 유무만 보고 판정 (기계 판정 단독)

- **Pros:** 모델 호출이 전혀 없어 빠르고 완전히 결정적이다.
- **Cons:** 주제만 비슷한 문서가 인용으로 붙어도 통과한다. 검색이 항상 무언가를 반환하므로 사실상 대부분이 통과한다.
- **Rejected because:** 출처 정확도가 1순위 지표인데, 이 방식은 "출처가 있다"만 보장하고 "출처가 맞다"는 보장하지 못한다.
- **Recheck if:** 골든셋으로 측정한 결과, 모델 판정 단계가 근거 정확도를 유의미하게 올리지 못하는 것으로 나오는 경우.

### 모델에게 전체 판정을 한 번에 맡김 (기계 판정 없이)

- **Pros:** 구현이 단순하다. 판정 로직이 프롬프트 한 곳에 모인다.
- **Cons:** 인용이 0개인 항목까지 모델에게 물어 호출 수가 늘고, 셀 수 있는 사실의 판정이 비결정적이 된다.
- **Rejected because:** 비용과 재현성 양쪽에서 손해인데 얻는 것이 없다.

### 상한 없이 uncovered가 빌 때까지 반복

- **Pros:** 근거를 찾을 수 있는 항목은 끝까지 찾는다.
- **Cons:** 인덱스에 근거가 없는 항목은 영원히 끝나지 않는다. 배치 실행의 종료가 보장되지 않는다.
- **Rejected because:** 같은 인덱스·같은 질의에서는 재검색 결과가 거의 같아, 반복해도 개선 없이 비용만 는다.

## Consequences

### Positive

- "근거 없으면 문장을 만들지 않는다"가 프롬프트 지시가 아니라 그래프 구조로 강제된다.
- 판정 실패가 조용한 품질 저하가 아니라 "근거 없음" 표시로 드러난다.
- 루프 종료 조건이 라우터 한 곳에 있어 그래프 정의만으로 설명된다.

### Negative

- 보수적 판정이라 실제로는 근거가 되는 문서가 "근거 없음"으로 떨어질 수 있다. 근거 누락률을 낮추는 대신 재현율을 희생하는 방향이다.
- 인용이 붙은 항목마다 Verifier 호출이 추가되어 질의 1건당 LLM 호출 수가 늘어난다 (실측: 4개 항목에 총 14회 호출). 다만 인용이 없는 항목은 기계 판정에서 걸러지므로 최악의 경우에도 항목 수만큼만 는다.

### Risks

- `min_citations=1`과 `max_revisions=2`는 근거를 갖고 고른 값이 아니라 출발점이다. 골든셋으로 측정하기 전까지 이 값들이 적절한지 알 수 없다.
- 재검색 힌트("이전에 못 찾았다")가 모델을 느슨하게 만들어, 2회차에서 뒷받침하지 않는 문서를 고를 유인이 생길 수 있다. 실측에서는 모두 여전히 근거 없음으로 판정돼 이 위험이 현실화되지 않았지만, 표본이 적어 결론을 내릴 수 없다.
- **재검색으로 근거를 새로 찾은 항목이 실측 0건이다.** 같은 인덱스에 거의 같은 검색어를 다시 던지므로 결과가 거의 같다. 검색어를 실제로 바꾸는(질의 재작성) 단계가 없다는 점이 구조적 한계이며, 현재 형태의 재검색은 비용만 늘릴 가능성이 있다. 코퍼스를 늘린 뒤에도 같은 양상이면 루프 설계를 다시 봐야 한다.

## Implementation

- [x] 기계 판정 + 모델 판정 2단계 (`make_verifier_node`)
- [x] 판정 실패 시 `uncovered` 처리
- [x] 재검색 시 `uncovered` 항목만 재조사 + 힌트 프롬프트 (`make_researcher_node`)
- [x] 항목별 인용 누적 병합 (`_citations_by_topic`)
- [x] 상한 도달 시 종료 (`route_after_verify`) + 단위 테스트
- [ ] `min_citations` / `max_revisions` 값 조정 — 골든셋 측정 후
- [ ] 재검색 시 질의 재작성(query rewriting) 도입 검토

## Reversibility

- **Reversible:** Yes
- **Rollback:** 판정 조건은 `make_verifier_node`의 인자(`min_citations`)와 프롬프트(`src/orchestrator/prompts.py`)에 모여 있고, 루프 종료는 `route_after_verify` 한 함수다. 조건 변경이 노드 구조나 그래프 배선에 영향을 주지 않는다.
- **Migration Cost:** Low

## Review Trigger

- 골든셋으로 측정한 결과 모델 판정 단계가 근거 정확도를 유의미하게 올리지 못하는 경우 — 기계 판정 단독으로 되돌릴지 재검토.
